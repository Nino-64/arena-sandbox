ATTACK 1 [MINOR] CLUTCH only ever fires on a spike's first pass, not when you re-dodge the same live spike
Where: `update()`, line 555 `if (!o.passed && o.prevD !== null && o.prevD > 0 && d <= 0 ...)` with `o.passed = true` inside and `o.prevD = d;` on line 567 (outside the gate). Spike lifetime is `life: rand(6, 8)` (line 484); objects are only removed at `o.age > o.life + 0.35` (line 551).
Problem: `o.passed` is set true on the first time the comet's angle crosses a spike and is never reset, so the CLUTCH branch runs at most once per spike for its whole life. But the comet laps the orbit roughly every `TAU/omega` = ~4.2 s at phase-1 speed (omega 1.5) and less as speed rises, while a spike lives 6–8 s. Worked example: a spike spawns at t=10 s with life 7 s; you ride its ring and cut off at the last moment on your first pass (~t=11.3 s) → CLUTCH awarded correctly. ~4.2 s later (~t=15.5 s, spike still alive until t=17) you come around to that same spike, get back onto its ring and cut off just as late again — an identical risky dodge — and get 0 points, because line 555 is gated by `!o.passed`. Collision (line 553) still fires on every pass, so you can even die on that second encounter, but the advertised reward ("you score a CLUTCH" whenever you ride a spike's ring and leave in time, per the writeup) silently never triggers again. The reward logic is asymmetric with the hazard logic.

ATTACK 2 [MINOR] The music scheduler's setInterval is created once and never cleared, running 40×/s for the life of the page
Where: `Music.start()`, line 368 `if (!this.timer) this.timer = setInterval(() => this.schedule(), 25);` and `Music.stop()`, line 370 `stop() { this.on = false; this.beats.length = 0; }` (no `clearInterval`).
Problem: Once the first run starts, a 25 ms interval is installed and is never torn down. `stop()` (called on death, line 516, and implicitly while on menu/over/pause) only flips `this.on = false`; the timer keeps firing `schedule()` 40 times a second forever, even while the player sits on the menu, the game-over card, or a paused screen, and even if they never play again. `schedule()` early-returns (line 372) so it is functionally harmless, but it is a real, permanent background cost in code the solution presents as polished and production-ready, and it means the scheduler can never be genuinely suspended, only short-circuited.

ATTACK 3 [MINOR] burst() trims the particle pool with O(n) Array.shift instead of the O(1) swap-pop used everywhere else
Where: `burst()`, line 440 `if (parts.length > 800) parts.shift();` versus the particle updater, line 1023 `parts[i] = parts[parts.length - 1]; parts.pop();` (O(1) swap-pop).
Problem: When the pool is at its 800 cap, every new particle calls `parts.shift()`, which re-indexes the entire array (O(n)). A death spawns 100 particles in one call (`burst(P.x, P.y, 70, ...)` + `burst(P.x, P.y, 30, ...)`, lines 514–515) and a Pulse spawns 18 per cleared spike (line 499); if the pool is already near 800 at that moment, that is dozens-to-hundreds of O(800) shifts in a single frame, while the rest of the engine deliberately uses O(1) swap-pop for the same job. It is inconsistent with the file's own fast path and an avoidable hitch at exactly the highest-particle moments (death, Pulse) the "juice" requirement is about.
