ATTACK 1 [MINOR] Restart is gated ~1.2 s behind the death animation, with no way to skip it
Where: `die()` -> `gameOver()` only fires when `time - G.dieAt > CFG.deathDelay` (deathDelay = 0.85 s, update() ~line 1082). `retry()` (line 1563) is `if (mode === MODE.OVER && time - overAt > CFG.retryGuard)` (retryGuard = 0.35 s). The canvas pointerdown handler (line 1528) calls `retry()` while `mode === MODE.DYING`, where it is a no-op because `retry()` requires `MODE.OVER`.
Problem: Requirement 1 states the game must have "instant restart loops." After every death the player is forced to sit through the full 0.85 s slow-motion sequence (there is no tap-to-skip; a tap during DYING does nothing), and then wait a further 0.35 s guard after the result card appears before any tap/key is accepted. That is ~1.2 s of mandatory, unskippable delay per death, which only half-meets "instant restart." The writeup's own line "a tap or a key press starts a new run at once" overstates this.

ATTACK 2 [MINOR] A second tab can flip the live run's core color and mute state mid-game
Where: `window.addEventListener("storage", e => { if (e.key === SAVE_KEY || e.key === null) syncFromOtherTab(); })` (line 1583). `syncFromOtherTab()` (line 1412) calls `Save.load()` unconditionally (no `mode` guard), which replaces `Save.data`, then `Sound.applyMute()`. `skin()`/`trailColor()` (lines 854-858) read `Save.data.skin` every frame.
Problem: The "Safe with two tabs open" claim only covers not losing shards/cores. Concrete counterexample: tab A is mid-run; in tab B you equip "Void" (or toggle mute). The `storage` event fires in tab A, `Save.load()` overwrites `Save.data` during the active run, and tab A's comet instantly turns black (and audio mutes/unmutes) mid-run. It is a visible glitch during play that the two-tab handling does not account for.

ATTACK 3 [MINOR] The live score and combo are hidden from assistive technology
Where: `<div id="hud" aria-hidden="true">` (line 348) wraps `#score` and `#combo`; it is never toggled back to visible.
Problem: The HUD holding the running score and combo multiplier is permanently `aria-hidden="true"`, so a screen-reader user gets no readout of score or combo while playing. The solution repeatedly claims "accessible UI" and gives menus/buttons ARIA labels, but the core in-game information is excluded from the accessibility tree.

ATTACK 4 [MINOR] Enter does not start a run from the title screen
Where: keydown handler, menu branch (line 1560): `if (mode === MODE.MENU && k === " ") { e.preventDefault(); startRun(); }` — only Space is handled. The over screen by contrast accepts Space/Enter/R (line 1555).
Problem: On the main menu, pressing Enter does nothing; the user must press Space or click Play. This is inconsistent with the result card (which accepts Enter) and undiscoverable, so a keyboard player who reaches for Enter to begin gets no response.
