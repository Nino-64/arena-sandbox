ATTACK 1 [MAJOR] On landscape phones, the shop's Back button and the game-over Skins/Menu buttons can't be reached, so the player gets stuck
Where: CSS `html,body{...touch-action:none}` combined with `.panel{...max-height:calc(100% - 8px);overflow:auto}`
Problem: Browsers combine `touch-action` from an element and all its ancestors (they take the intersection). Because `body` has `touch-action:none`, touch scrolling is turned off for every descendant. That includes the `overflow:auto` panels, which the solution relies on when a panel is taller than the screen. Rough heights from the CSS: the Skins panel is about 430 px (padding 54, eyebrow + h2 about 75, wallet about 28, a 2×3 skin grid about 214, Back button 62). The game-over panel is about 550 px. A landscape phone such as an iPhone SE (667×375, roughly 320–340 px usable once the 16 px screen padding is taken off) gets max-height of about 335 px. Counterexample: rotate the phone to landscape, open Skins from the menu, and the Back button sits below the clipped edge. Swiping does not scroll the panel. The only other way out is `Escape`, and a phone has no keyboard, so the player has to reload the page. On the game-over panel the "Skins" and "Menu" row is cut off the same way. The checklist claims the layout works "from 375 px phone width up to desktop" but only covers portrait.

ATTACK 2 [MAJOR] CLUTCH points can be farmed with no risk by double-tapping, which skews the score, the saved high score and XP
Where: `if (active && o.ring !== P.ring && o.ring === P.prevRing && G.t - P.swapT < 0.35)` in `update()`, with `P.blend += (P.ring - P.blend) * Math.min(1, dt * 22)`
Problem: The check only asks whether your last swap started on the spike's ring. It never asks whether you were actually in danger. Counterexample: you are on the outer ring and a live spike on the inner ring is about 0.1 s ahead. Double-tap about 20 ms apart. After the first tap, ring=0 and prevRing=1. After the second, ring=1, prevRing=0 and swapT is recent. The smoothing (time constant about 45 ms) pulls the comet only about 36% of the way inward and then back. It never comes near the inner spike, yet you still get the CLUTCH +25×mult. That is 2.5× a shard pickup, and it works on every spike on the other ring, about one per second late in a run. The best strategy becomes spamming double-taps, not dodging. The inflated score goes into `S.best` and `S.xp`, so the persisted high score and progression stop meaning anything. The solution describes CLUTCH as a reward for a close escape ("Switch off a spike's ring less than 0.35 s before you pass it"), and the code doesn't check for that.

ATTACK 3 [MAJOR] A live "NEW BEST!" is shown and then thrown away when the run ends any way other than a crash
Where: `updateHud()` pops "NEW BEST!" and turns BEST gold mid-run. But `KeyR` during play calls `startGame()`, `#pauseRestart` calls `startGame`, and `#pauseMenu` calls `toMenu`. None of these goes through `endRun()`.
Problem: Only `endRun()` writes best, XP, shards and runs to localStorage. Counterexample: beat your record, so the HUD shows "NEW BEST!" and BEST tracks your score. Then press R, or pause and choose Restart or Menu. The record, every shard collected in that run and the XP are all lost. `S.plays` doesn't go up either. Closing or reloading the tab mid-run also loses everything, because the auto-pause on blur/visibility never saves. Requirement 4 asks for "Save systems (high scores, progression...)", and the game tells the player a record was set and then never saves it.

ATTACK 4 [MINOR] The testing claims contradict each other
Where: Checklist row 6: "I did not re-run the browser smoke test on this revision because no browser is available here". Assumptions: "Tested in headless Chromium."
Problem: The delivered file was never run in a browser, but the Assumptions section presents it as tested. The user can't trust the "zero console errors" verification for the code they actually get. Changes to the main loop's sub-stepping and to the retry/input paths were shipped unverified.

ATTACK 5 [MINOR] An instant retry after a record-breaking crash plays the victory fanfare over the new run
Where: `retry()` → `if (state === 'dying' && !G.ended) { G.ended = true; endRun(); }` then `startGame()`; `endRun()` ends with `if (isBest) SFX.fanfare();`
Problem: Counterexample: set a new best, crash, and tap within 0.3–0.8 s (the "instant restart" path the solution promotes). `endRun()` builds and shows the results screen and schedules the five-note fanfare. `startGame()` hides that screen in the same tick, so the player never sees the NEW BEST badge or the earned/unlock line. The fanfare then plays over the first second of the new run, with nothing on screen to explain it. The fastest restart path loses the only feedback that a record was set.
