ATTACK 1 [MAJOR] Save system silently loses the high score with two tabs open
Where: `persist()` (lines 389-391), `loadSave()` (line 372), and the event registrations (lines 985-1017, which contain no `storage` listener).
Problem: The required save system (requirement 4: "high scores, progression ... using LocalStorage") loses data in a realistic scenario. `persist(data = save)` writes the in-memory `save` object straight to localStorage without ever re-reading what is already there, and nothing listens for the `storage` event, so an open tab never learns of another tab's writes. Opening a single `index.html` in two tabs is trivial for a web game. Counterexample: Tab A and Tab B both load `best: 100`. In Tab A you play a run scoring 500 and die -> `bankRun()` sets `save.best = 500` and `persist()` writes `best: 500` to storage. In Tab B, whose in-memory `save.best` is still 100, you then play any run (say score 20) and die -> `bankRun()` does `save.best = Math.max(100, 20) = 100` and `persist()` overwrites storage with `best: 100`. The user's new best of 500 is gone with no warning. The same clobber drops `totalOrbs`, `games`, `bestCombo`, and newly `unlocked` cores earned in the other tab.

ATTACK 2 [MINOR] Unbounded glow-sprite cache keyed on a continuously eased hue
Where: `glowSprite()`/`glowCache` (lines 512-528); orb render color `c = accSoft` (line 1144) with `accSoft = hslToRgb(G.hue, 0.6, 0.8)` (line 1029) and `G.hue` eased every frame (line 1287).
Problem: `glowSprite` creates and permanently caches a 128x128 offscreen canvas per distinct color string, and is never evicted. Orb glows are drawn with `accSoft`, derived from `G.hue`, which is eased continuously toward each lap's new target. During every lap's color transition `G.hue` changes by a fraction of a degree per frame, producing a new integer-RGB triple (and thus a new cache key and a new 128x128 canvas) on most frames of the transition. Over a long run spanning many laps the cache accumulates a few hundred of these canvases (tens of MB) that are kept for the life of the page, pressuring memory on low-end mobile during the exact "one more run" marathon sessions the game is designed to encourage. (The player skin and hazard glows are bounded; only the hue-driven orb glow leaks keys.)

ATTACK 3 [MINOR] Death sound's tail is cut to silence by too-short noise buffer
Where: noise buffer length `Math.floor(this.ctx.sampleRate * 1)` (line 420); playback `src.start(t, Math.random() * 0.5)` (line 456); `Sfx.death` uses `Audio.noise({ dur: 0.7, ... })` (line 480).
Problem: The procedural noise buffer is exactly 1.0 s and the BufferSource is not looped, but every noise is played from a random start offset of up to 0.5 s into that buffer. The death noise has `dur: 0.7`. When the random offset is near 0.5 s, only 0.5 s of buffer remains (1.0 - 0.5), so the source runs out of samples and emits silence for roughly the final 0.2 s while the gain envelope is still open and ramping. The result is an inconsistent, randomly-truncated death sound - the single most important piece of feedback in a one-hit game - rather than the intended 0.7 s swell. The fix is a buffer of at least `sampleRate * 1.5` or clamping the start offset to `1 - dur`.
