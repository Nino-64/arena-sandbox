ATTACK 1 [MAJOR] Save system fails silently when localStorage is blocked, with zero feedback
Where: `write() { try { localStorage.setItem(SAVE_KEY, JSON.stringify(this.data)); } catch (e) { /* ignore */ } }` and `load()`'s `catch (e) { /* storage blocked or corrupt: keep defaults */ }`.
Problem: Requirement 4 is "Save systems (high scores, progression, unlockables using LocalStorage)." In a common environment — Firefox Private Browsing (and other sandboxed/blocked-storage contexts) `localStorage.setItem` throws — every write is swallowed by the empty catch. The result: best score, shard bank, purchased cores and achievements never persist across a reload, and the player is never told. Nothing in the UI (menu, result card, or a toast) indicates the save is non-functional, so the user loses all progress on refresh with no explanation. The save requirement is silently unmet in a realistic, common case. Counterexample: open the game in Firefox private mode, set a high score and buy a core, reload → everything is gone, no warning shown.

ATTACK 2 [MINOR] A new high score (and the run's shards) is lost if the tab is closed during the death animation
Where: `gameOver()` — `d.best = G.score; ... d.bank += G.shards; ... Save.write();` is the only place best/bank are persisted, and `die()` sets `mode = MODE.DYING` with `gameOver` firing only after `CFG.deathDelay` (0.85s) plus the 0.12s hit-stop.
Problem: Best score and earned shards are written only in `gameOver()`, which runs ~0.95s after the fatal hit (slow-mo death sequence). If the player closes or navigates away during that ~1s window — plausible right after a crushing death — the new best and the run's shards are never saved. Requirement 4 names "high scores"; this is a concrete, reproducible loss window. (Achievements earned mid-run are saved immediately, so the inconsistency is also visible: the badge persists but the score that triggered it does not.)

ATTACK 3 [MINOR] No multi-tab save reconciliation; two tabs clobber each other's progress
Where: There is no `window.addEventListener("storage", ...)`; `gameOver()`/buy flows do `Save.write()` from the in-memory `Save.data` loaded once at startup.
Problem: Open the game in two tabs. In tab A, buy a core (bank decremented, written). In tab B (whose `Save.data` was loaded before the purchase), finish any run → `gameOver()` writes tab B's stale snapshot, reverting the purchase and restoring the spent shards. Last-writer-wins silently corrupts the saved progression. This is a concrete data-loss scenario against the save requirement.

ATTACK 4 [MINOR] `new AudioContext()` is unguarded; a construction failure kills the first interaction and the game never starts
Where: `unlock()` — `this.ctx = new AC();` with the surrounding node setup, inside the `if (!this.ctx)` block. There is no try/catch here (only `if (!AC) return;` guards total absence of the API).
Problem: `Sound.unlock()` is the first statement in `startRun()`, the Play button handler, and the canvas `pointerdown`/`keydown` handlers. If the `AudioContext` constructor throws (it can under certain privacy/sandbox settings, or when the per-page context limit is hit), the exception propagates out of the click handler; `newRun()`/`mode = MODE.PLAY`/`showScreen(null)` after it never execute, so clicking Play does nothing and the game is unstartable. The solution's own claim that "a broken or blocked save falls back to defaults" is applied to storage but not to audio construction, which has no equivalent fallback.

ATTACK 5 [MINOR] False robustness claim: "a single bad frame can never freeze the game"
Where: Writeup: "The main loop also schedules the next frame before doing any work, so a single bad frame can never freeze the game," matching `frame(now){ requestAnimationFrame(frame); ... update(dt); render(); }`.
Problem: Scheduling RAF first only prevents the loop from being *descheduled*; it gives no protection against the ordinary failure mode where `update()` or `render()` throws from a persistent bad state — the same exception then recurs every frame, no simulation advances, and the screen is frozen for the user. There is no try/catch in `frame`/`update`/`render` and no `window.addEventListener("error", ...)` boundary anywhere in the file, so the stated guarantee ("can never freeze") does not hold; a recurring throw freezes the game with no recovery path or visible error.
