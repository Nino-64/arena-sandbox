ATTACK 1 [MAJOR] Live spikes can be tunneled through at low frame rate, breaking the only fail condition
Where: frame loop line 919 `const real = Math.min(0.05, ...)`, update line 492 `P.a += G.omega * G.dir * dt`, collision line 510 `if (active && dist < (PR + HR * 0.75) * U) die('SPIKED')`.
Problem: Collision is a single point-distance sample per frame with no swept/interpolated check, and dt is clamped to 0.05 s (20 fps). The player's linear speed is `omega * pr`; omega climbs to 3.3 and the outer ring (R1 = base*0.78) is large. Counterexample: a 375px-wide phone (base≈187, R1≈146, U≈0.6) running at a common mobile 30 fps (dt≈0.033). Per-frame travel on the outer ring = 3.3*146*0.033 ≈ 16 px, while the collision radius = (PR+HR*0.75)*U = (10+9)*0.6 ≈ 11 px. The player jumps from one side of a live spike to the other in a single step, so it passes through an active same-ring spike with no `die()` call. At 20 fps the gap is ~26 px vs ~11 px, worse. The core (and only) way to lose silently fails on low-end/throttled devices.

ATTACK 2 [MAJOR] Moving spikes can block both rings at once, producing unavoidable deaths despite the stated fairness guarantee
Where: spawnHazard line 444-446 and the "Fairness rules built in" claim (lines 968-969: "always leave a passable gap on the other orbit ... so there is always a way through when it spawns"), combined with moving hazards line 449 `va: moving ? rand(0.2,0.45)*...`.
Problem: The passable-gap check runs only at spawn time. Hazards given `va` drift at up to 0.45 rad/s for a 6-8 s life, i.e. up to ~3.6 rad of travel - more than half the circle. Two independently-spawned live spikes, one per ring (each legal at its own spawn moment), can therefore drift until both sit within collision range of the same arrival angle. When the player reaches that angle both rings are blocked: switching (the only control) cannot help, and the 0.65 s telegraph gives no escape because both spikes are already past telegraph. The game's own fairness claim is scoped to "when it spawns" and does not hold once `va != 0`, so the player loses runs to deaths they could not prevent.

ATTACK 3 [MINOR] "Instant restart" is a forced ~1.4 s wait, and the self-reported ~1 s figure is wrong
Where: die line 477 `G.hitstop = 0.11`; frame loop line 928 `if (G.deadT > 0.95 && !G.ended) ... endRun()`; canRetry line 655 `state === 'over' && performance.now() - overAt > 450`. Checklist row 1 claims "about 1 s."
Problem: Requirement 1 asks for "instant restart loops." After death, `endRun` only fires once `G.deadT > 0.95` s, then `overAt` is stamped and `canRetry()` additionally rejects any input for a further 450 ms. Minimum time from death to an accepted retry is ~0.95 + 0.45 ≈ 1.4 s, not the "about 1 s" the checklist states, and not "instant." Every retry eats a mandatory ~1.4 s dead zone.

ATTACK 4 [MINOR] HUD "BEST" is frozen for the whole run and never reflects beating it live
Where: startGame line 428 `$('#hbest').textContent = S.best;` is the only write to the in-run BEST readout; `S.best` is updated only later in endRun line 558.
Problem: The in-game HUD BEST is set once at run start from the pre-run high score and never updated during play. A player who passes their previous best mid-run still sees the old number until the game-over screen, so the "BEST" indicator is stale/misleading for the entire record-setting run.
