ATTACK 1 [MINOR] No flip debounce: double-registered taps cancel a dodge
Where: `cv.addEventListener('pointerdown', e => { ...; press(...); })` (line 493) → `press()` → `flip()` (lines 200-206). Keydown only guards `if (e.repeat) return;` (line 498); there is no time/debounce guard on pointer input.
Problem: `flip()` does `G.lane ^= 1` unconditionally on every pointer event. On a touchscreen a two-finger tap or an accidental palm/double contact fires two `pointerdown` events in the same moment, so the lane is flipped twice and ends up unchanged — the player presses to dodge and does not move, then dies on the obstacle they tried to avoid. The same handler also fires for right-click and middle-click (no `e.button` filter), so a stray right-click during play triggers an unwanted flip that can cause a death. For a game sold as "one tap" on phone and desktop this is a real responsiveness gap; the opponent's own prose does not account for it.

ATTACK 2 [MINOR] "Patterns keep getting tighter until you crash" is false — difficulty plateaus
Where: Prose line 3 ("The orbit keeps getting faster and the patterns keep getting tighter until you crash") vs code line 249 `G.w = Math.min(1.7 + G.score * 0.01, 3.2);` and line 237 `const d = Math.min(G.score / 160, 1), ...`.
Problem: Speed is hard-capped at 3.2 rad/s, reached at score 150 (1.7 + 150*0.01 = 3.2), and the pattern-difficulty term `d` is clamped to 1 at score 160. For any run past ~160 points — easily reached — nothing gets faster or tighter; the game runs at a fixed difficulty indefinitely. Combined with the author's own claim (line 38) that a scripted bot "played 20 s at the highest difficulty without dying," a skilled player faces a flat, survivable steady state with no escalation, contradicting the stated escalating loop.

ATTACK 3 [MINOR] False claim that arcs spawn "more than ½ an orbit ahead"
Where: Design note line 38 ("arcs spawn more than ½ an orbit ahead of you") vs spawn trigger line 254 `while (G.next < G.a + 2.6) spawn();`.
Problem: Obstacles become present when they are within 2.6 rad ahead of the player, so the minimum lead at spawn is 2.6 rad ≈ 149°, which is less than half an orbit (π ≈ 180° ≈ 3.14 rad). The claimed ">½ orbit" lead is numerically wrong. At the capped speed of 3.2 rad/s this is 2.6/3.2 ≈ 0.81 s of lead, not the ~1 s the half-orbit framing implies.

ATTACK 4 [MINOR] prefers-reduced-motion is read once and never updates
Where: Line 72 `const RM = matchMedia('(prefers-reduced-motion: reduce)').matches;` — captured once at load, used throughout (shake/flash scaling in `die()` line 214, `draw()` line 425, close-call line 267). No `change` listener is attached.
Problem: If a motion-sensitive user enables "reduce motion" in their OS while the tab is already open (or disables it), the setting has no effect until a full page reload — the screen shake and white flash keep firing at full strength. The accessibility accommodation the solution advertises ("The shake and flash are toned down when the system asks for reduced motion," line 24) silently fails to track a mid-session change.
