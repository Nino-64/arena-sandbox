ATTACK 1 [MAJOR] A mouse click on the mute button takes over the Space key, so Space stops launching or starting the game
Where: keydown handler: `const onButton = e.target instanceof HTMLButtonElement && !!e.target.closest('.screen.show, .hud'); if ((k === ' ' || k === 'Enter') && onButton) return;`, together with `muteBtn.addEventListener('click', toggleMute);` (the mute click never calls blur)
Problem: Chrome and Firefox (Windows/Linux) give a <button> focus when it is clicked. The mute button sits in `.hud`, so after a player clicks it, every later Space or Enter keydown matches `onButton` and returns early. The browser then fires a click on the focused button, which calls toggleMute. Counterexample: start a run, click the speaker icon with the mouse, then press Space to jump. The orb does not launch, the sound toggles back on, and the planet's collapse timer keeps running until the run ends with "Your planet collapsed". The same thing happens on the main menu: click mute, press Space, and the game toggles sound instead of starting. This contradicts the controls table ("Launch ... Space / ↑ / W / Enter") and the claim that keyboard input was verified.

ATTACK 2 [MINOR] For 250 ms after a restart, taps land on the fading screen, so the first launch tap of a new run is ignored
Where: `.screen{... opacity:0;visibility:hidden;transition:opacity .25s ease,visibility .25s}` with `$('over').addEventListener('pointerdown', ... tryRestart())` and `canvas.addEventListener('pointerdown', ... if (state === 'play') launch())`
Problem: When `visibility` transitions from visible to hidden, the element stays `visible` (and keeps receiving hits) for the full 0.25 s. After a tap-to-retry, `state` is already 'play', but any tap in the next 250 ms hits the `#over` section instead of the canvas. There `tryRestart` does nothing because `state !== 'over'`, and `launch()` is never called. Counterexample: a fast player taps once to retry and taps again about 150 ms later to jump, and the jump is lost. Pressing Play on the menu has the same problem. This works against requirement 1, "instant restart loops", on touch, which is the main input the doc targets ("Tap anywhere").

ATTACK 3 [MINOR] Touch players have no way to restart mid-run, and a death always costs at least 1.2 s before a retry
Where: Controls table: "Restart mid-run | — | R"; and the keydown handler `if (state === 'play' || state === 'over') startRun();` (R is ignored while `state === 'dying'`); `deathT = 0.9` plus `overReadyAt = performance.now() + 300`
Problem: Requirement 1 asks for "instant restart loops". On phones, which the doc names as a target ("desktop or mobile", "checked at phone size"), a run cannot be restarted at all except by dying. Every death then forces 0.9 s of death animation plus a 0.3 s input lock before a tap is accepted. On desktop, pressing R during the 0.9 s dying phase also does nothing. The doc's claim that "a tap or Space starts a new run in the same frame" is true only after this 1.2 s delay.

ATTACK 4 [MINOR] The claim "At most 700 particles" is false
Where: Design notes: "at most 700 particles"; code: only `burst()` checks `particles.length < 700`. `launch()` pushes 14 particles in its own loop with no check, `ring()` pushes with no check, and the flight trail `particles.push(...)` in `update()` runs about 70% of frames with no check.
Problem: A death adds 100 to 190 particles through `burst`, then 1 to 2 rings with no cap check, while trail particles keep being added. So the array can go over 700, and the performance guarantee in the write-up does not match the code. The effect in play is small, but it is a factual error in the "Performance" claims.

ATTACK 5 [MINOR] Pinch-zoom is disabled, which goes against the web-design-guidelines the user asked for
Where: `<meta name="viewport" content="width=device-width,initial-scale=1,viewport-fit=cover,user-scalable=no">`
Problem: The user asked the solution to follow `web-design-guidelines`. Standard web interface guidelines (for example Vercel's, which that skill name appears to refer to; this is an assumption because the skill is not installed) say never to disable browser zoom. `user-scalable=no` stops low-vision users from zooming the menus and the results and skins panels. The doc's "UI and accessibility" section presents the page as accessibility-compliant without mentioning this.
