ATTACK 1 [MAJOR] Shockwave gaps and player-tracking meteors are independent, so a one-input game produces unavoidable deaths
Where: spawnMeteor aim (lines 905-909, uses G.theta/G.dir/G.omega), spawnPulse gap (line 923: `const gap = G.theta + rand(-2.0, 2.0)`), pulse hit (line 1147), meteor hit (line 1124). Timers: meteors every ~0.29-0.55 s at diff=1 plus 25% double (line 1056), pulses every ~4.2 s (line 1058).
Problem: The task requires a "satisfying core gameplay loop." The player has exactly one lever (reverse direction) and is locked to the ring at R=150. A shockwave forces the player INTO its safe gap (survive only if `|angDiff(theta, gap)| < half` when `|p.r-R|<6`), while a meteor is aimed AT the player's predicted position. The two spawners share no coordination, so a reachable state exists where the pulse's safe gap and an arriving aimed meteor sit on the same arc of the ring: threading the pulse (staying near the gap) walks you into the meteor, and dodging the meteor (reversing away) walks you out of the gap into the shockwave. With a single input you cannot satisfy both, so the death is not the player's fault. At diff=1 (after 150 s) meteors arrive 2-3x/sec concurrently with pulses, making this overlap routine rather than rare. There is no fairness check anywhere in the code to prevent it.

ATTACK 2 [MINOR] Reduced-motion users still get screen shake and full-screen flashes
Where: `@media (prefers-reduced-motion:reduce)` block (lines 253-256); `shake: prefersReduced ? 0.3 : 1` (line 474); Fx.shake/doFlash multiply by `save().settings.shake` (lines 830-831); canvas shake applied at lines 1201-1204; full-screen additive flash at lines 1385-1389.
Problem: The reduced-motion media query only disables CSS transitions/keyframes on DOM elements. All of the canvas "juice" (trauma shake, zoom punch, white/colored full-screen flash on every death, multiplier, and power-up) is gated solely on `settings.shake`, which defaults to 0.3 under reduced motion, not 0. So a user who set OS reduced-motion — the standard signal to suppress exactly this kind of motion and flashing — still receives 30% screen shake and ~0.16-alpha full-screen flashes. The presence of the media query and the documented "defaults to 30%" imply the preference is honored for motion, but the flashing (a genuine photosensitivity concern) is never suppressed, only attenuated.

ATTACK 3 [MINOR] A save written by another tab clobbers the live run's active settings mid-game, and the audio graph is never resynced
Where: storage event handler, lines 1709-1716 (`Store.data = fresh;` with only `if (G.state === 'menu') UI.refreshTitle()` afterward). Audio reads settings in Sound.apply (line 608) which is not called here.
Problem: While Tab A is mid-run, if Tab B commits any settings change (e.g. the user drags the shake slider to 0 or changes volume, which commit on 'change', or equips a different skin), Tab A's handler replaces its entire `Store.data` with Tab B's. The in-progress run's feel changes immediately: `Fx.shake` now multiplies by the new shake value, and `currentSkin()` returns the newly-equipped skin, so the comet's color and all juice change in the middle of play. Worse, the handler never calls `Sound.apply()` or `UI.syncSettings()`, so a volume change leaves `Store.data.volume` updated but the audio gain still at the old value — and when Tab A's run ends, `finishRun()` commits this out-of-sync state back to storage. The doc bills cross-tab sync as a safety feature, but it mutates live gameplay state and desynchronizes the audio graph from the saved settings.
