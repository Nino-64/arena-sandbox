ATTACK 1 [MINOR] "Instant restart" is gated ~1.35 s for tap/touch, and the only truly-instant restart is keyboard-only
Where: Task req 1 ("Pure, self-contained, playable game with instant restart loops"). Code: `if (dyingT >= 0.9) showOver();` (update, ~line 909) and `case 'over': if (realTime - overAt >= RESTART_GUARD) startRun();` (primaryAction, ~line 1361) with `RESTART_GUARD = 0.45`. The writeup itself states: "Taps are ignored during the 0.9 s death animation and for 0.45 s after results appear."
Problem: A tap/Space restart does nothing until 0.9 s (death animation) + 0.45 s (guard) = 1.35 s after death. The genuinely-instant path is the R key (restartNow bypasses the guard), but R is a keyboard input unavailable on touch devices. On mobile the fastest restart is the on-screen Retry button, which cannot fire until the results screen renders at 0.9 s. So the "instant restart loop" the task asks for is not instant for the game's primary (tap/touch) input: minimum 0.9 s, up to 1.35 s.

ATTACK 2 [MINOR] Documented start controls (arrows / WASD) do nothing on the main menu
Where: Controls table in the writeup: "| Hop orbit / start / retry | Tap, click, Space, Enter, arrows, WASD |". Code (keydown, ~line 1412): `if (state === 'menu' && k !== 'Space' && k !== 'Enter' && k !== 'NumpadEnter') return;`.
Problem: On the menu, when focus is not on a control, pressing an arrow key or W/A/S/D hits this guard and returns without calling `primaryAction()`, so the game does not start. Only Space/Enter (or tap/click) start a run from the menu. Counterexample: load the page, press the Up arrow (or W) — nothing happens, contradicting the controls table that lists "arrows, WASD" as a start input. (Arrows/WASD do work to retry on the game-over screen, so the behavior is inconsistent and the doc is wrong specifically for the menu.)

ATTACK 3 [MINOR] A single 32-voice cap is shared between SFX and the music scheduler, so the adaptive beat (req 3) can silently drop out under load
Where: `const MAX_VOICES = 32;` and the early-returns `if (!live() || voices >= MAX_VOICES) return;` in both `tone()` (~line 487) and `noise()` (~line 500), with `scheduleStep()` (the music) calling the same `tone`/`noise`.
Problem: The voice counter is global across sound effects and the music loop. During a dense moment (a long chain firing `collect`/`multUp` plus `near` whooshes while the beat, hats, bass and arpeggio are also scheduling notes), the `voices >= MAX_VOICES` check makes whichever note is scheduled next return silently. Because music notes are scheduled slightly ahead via `scheduleStep`, they are the ones that will frequently hit the cap and be skipped, so the kick/bass of the "adaptive beat" feature advertised under requirement 3 can cut out exactly when the game is most intense. There is no reservation of voices for the music bus to prevent SFX from starving it.
