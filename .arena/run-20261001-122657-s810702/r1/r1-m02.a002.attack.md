ATTACK 1 [MAJOR] Difficulty stops rising about 23 s into a run, but the game keeps saying "faster" on every lap
Where: `omega0: 1.7, omegaStep: 0.16, omegaMax: 2.9`; `const lapK = Math.max(0.85, 1 - 0.03 * (G.lap - 1));`; `setBanner(`Lap ${G.lap}`, '+5 · faster');`; and the README line "Every full lap makes the game faster".
Problem: Speed is min(2.9, 1.7 + 0.16*(lap-1)), so it reaches the 2.9 cap at lap 9 (1.7 + 0.16*8 = 2.98, clamped). Shard spacing reaches its 0.85 floor at lap 6. Laps 1-8 take 2*pi*(1/1.7 + 1/1.86 + ... + 1/2.82), about 22.9 s. After that the game never changes: same speed, same gap distribution, same mechanics. The only change is a 47 degree hue shift. Yet onLap() still shows "+5 · faster" on lap 10, 11, 12 and later, and the README says every lap makes the game faster. Both statements are false. The author's own bot "survived 40 runs × 60 s at 2.9 rad/s with no deaths", which shows the capped state can be survived forever. So a long run ends only through a human lapse, with nothing new to push toward. That weakens the "ultra-addictive" core loop the task asks for. The fix is checkable: show "faster" only when omegaFor(lap) > omegaFor(lap-1), or keep difficulty rising after lap 9.

ATTACK 2 [MAJOR] Restarting or quitting mid-run throws away the whole run's progress, including a new high score
Where: `$('btnRestart').addEventListener('click', start);`, `$('btnQuit')... toMenu()`, and the `KeyR` handler `if (G.state === 'play' || G.state === 'paused' ...) start();`. All save writes happen only in `die()`.
Problem: Requirement 4 asks for "Save systems (high scores, progression, unlockables using LocalStorage)". The game writes `save.games`, `save.totalOrbs`, `save.maxLap`, `save.bestCombo` and `save.best` only in die(). start() and toMenu() call resetRun() without saving anything. Counterexample: a player reaches lap 7 with 320 points (old best 200) and 60 orbs, pauses, then presses Restart or Menu, or presses R. Best stays at 200, the 60 orbs never count toward Tide ("Collect 150 orbs"), and lap 7 never counts toward Volt. A run that is paused (P, or the automatic pause on tab blur) and then closed is also lost entirely. That conflicts with the README's claim that "closing the tab ... loses nothing". The pause menu advertises Restart and Menu, so this is a normal UI path that silently drops progress.

ATTACK 3 [MINOR] After a long run, every restart sweeps through several full rainbow cycles in about a second
Where: `onLap()`: `G.hueTarget = 205 + (G.lap - 1) * 47;` `resetRun()`: `G.hueTarget = 205;` (G.hue is not reset); `update()`: `G.hue = lerp(G.hue, G.hueTarget, 1 - Math.pow(0.02, dt));`
Problem: hueTarget grows without limit, and hslToRgb wraps it modulo 360. After dying on lap 20, G.hue is 205 + 19*47 = 1098. Retry or Menu sets hueTarget back to 205, so the lerp (time constant 1/ln 50, about 0.26 s) runs backward through 893 degrees, about 2.5 full color wheels, in roughly one second. The ambient glow, orbits, orbs, banner and accent ripples all strobe through the spectrum right at run start, exactly when the player needs to read the first shards. reducedMotion does not limit this. For a "highly polished" game this is a visible glitch. Setting G.hue = 205 in resetRun, or lerping along the shortest arc modulo 360, fixes it.

ATTACK 4 [MINOR] The "optional" gold orb is effectively required, because skipping it breaks your combo
Where: `generate()`: `if (gap >= 0.8 && r < 0.2) { /* Gold orb on the risky orbit */ ... ring: nxt, gold: true ...}`, and the miss handler in step(): `else if (G.angle - o.a > T.orbMissAngle) { o.missed = true; ... G.combo = 0; }` (no gold exception).
Problem: The README sells gold orbs as a risk/reward choice ("Gold orbs sit on the risky orbit and score double"). In the no-swap case (nxt === ring), the gold orb sits on the shard's own orbit, halfway between two shards on that ring. A player who plays it safe and stays on the safe line loses their whole multiplier, up to ×10. So declining the risk costs far more than taking it gains (2× one orb against resetting all later orbs to ×1). That removes the choice the mechanic is described as offering. The miss branch should skip `G.combo = 0` when `o.gold`.

ATTACK 5 [MINOR] The test claim about where the gaps are smallest is false
Where: "That reached lap 28, where the gaps between shards are at their smallest."
Problem: lapK = max(0.85, 1 - 0.03*(lap-1)) reaches its 0.85 floor at lap 6, and speed caps at lap 9. From lap 9 on, lap 28 generates exactly the same distribution as lap 9. It is not harder and not tighter. The claim implies the fairness test covered growing difficulty that the code does not have. That matters because the README's "Fairness" section relies on this test as proof.
