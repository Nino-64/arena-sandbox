# Ton hub devient un OS personnel : 5 agents et le noyau qui les relie

Ton hub a déjà les deux pièces maîtresses d'un OS personnel : des **casiers**, où l'information arrive triée, et un **journal d'événements en temps réel**. J'en fais le système nerveux de l'ensemble. Les cinq agents ci-dessous sont des blocs indépendants : ils lisent les casiers, écrivent dans le journal et se parlent à travers lui. Pour chacun, tu as la vision complète, puis ce que tu peux en coder dès aujourd'hui.

## 2. Le noyau (à coder en premier, environ une demi-journée)

Le noyau n'est pas un agent, c'est le code commun à tous. Chaque agent est un process Python qui dispose de quatre éléments :
- un **manifeste**, qui fixe ses droits ;
- des **tâches planifiées**, gérées par APScheduler. Elles sont stockées dans SQLite, ce qui permet de rattraper au démarrage les tâches manquées ;
- des **abonnements** à des sujets du journal, avec un curseur sauvegardé : après un redémarrage, l'agent reprend exactement où il s'était arrêté ;
- un **signal de vie**, émis dès le démarrage puis chaque minute.

**2.1 Un seul contrat d'événement.** Le journal sert à la fois d'écran de contrôle, de bus entre agents et de registre d'audit. En plus de l'agent, du titre et du contenu, chaque événement porte six champs clés :

| Champ | Rôle |
|---|---|
| `topic` | sujet, de la forme `domaine.objet.verbe` (ex. `finance.exposure.updated`) |
| `severity` | niveau d'importance (voir 2.7) |
| `entities` | objets concernés (voir 2.3) |
| `dedup_key` | rend la publication idempotente : une même clé, pour un même agent et un même sujet, ne crée qu'un seul événement |
| `correlation_id` | identifiant commun à tous les événements nés d'un même fait |
| `hops` | compteur qui coupe les boucles |

Version minimale, testée : doublons, collisions entre agents, boucles, 8 process concurrents, curseurs, chien de garde, sortie de veille.

```python
# noyau/bus.py — journal, bus entre agents et signaux de vie : un fichier SQLite, zéro serveur
import json, os, sqlite3, time, uuid
from contextlib import closing

DB_PATH = os.path.expanduser(os.environ.get("HUB_DB", "~/hub/hub.db"))  # même base pour tous

def _connect():
    # une connexion par appel : sûr depuis plusieurs threads et plusieurs process
    db = sqlite3.connect(DB_PATH, isolation_level=None, timeout=10)
    db.row_factory = sqlite3.Row
    return closing(db)

os.makedirs(os.path.dirname(DB_PATH), exist_ok=True)
with _connect() as db:
    db.execute("PRAGMA journal_mode=WAL")  # lectures possibles pendant les écritures
    db.execute("""CREATE TABLE IF NOT EXISTS events(
      seq INTEGER PRIMARY KEY AUTOINCREMENT, id TEXT, ts REAL, agent TEXT,
      topic TEXT, severity TEXT, title TEXT, entities TEXT, payload TEXT,
      dedup_key TEXT UNIQUE, correlation_id TEXT, hops INTEGER)""")
    db.execute("""CREATE TABLE IF NOT EXISTS agents(
      name TEXT PRIMARY KEY, interval_s REAL, last_beat REAL,
      last_success REAL, cursor INTEGER DEFAULT 0)""")

def emit(agent, topic, title, severity="info", entities=(), payload=None,
         dedup_key=None, correlation_id=None, hops=0):
    """Publie un événement. Renvoie (id, statut) : 'nouveau', 'doublon' ou 'boucle'."""
    if hops > 3:  # coupe-circuit anti-boucle : la coupure est tracée, jamais silencieuse
        emit(agent, "bus.loop.cut", f"Boucle coupée : {topic}", "erreur",
             payload={"topic": topic}, correlation_id=correlation_id,
             dedup_key=f"{correlation_id}:{topic}")
        return None, "boucle"
    # clé propre à l'agent et au sujet : deux agents ne peuvent pas se télescoper
    key = None if dedup_key is None else f"{agent}|{topic}|{dedup_key}"
    eid = uuid.uuid4().hex
    with _connect() as db:
        cur = db.execute(
            "INSERT OR IGNORE INTO events(id, ts, agent, topic, severity, title,"
            " entities, payload, dedup_key, correlation_id, hops)"
            " VALUES (?,?,?,?,?,?,?,?,?,?,?)",
            (eid, time.time(), agent, topic, severity, title,
             json.dumps(list(entities)), json.dumps(payload or {}, ensure_ascii=False),
             key, correlation_id or eid, hops))
        if cur.rowcount:
            return eid, "nouveau"
        old = db.execute("SELECT id FROM events WHERE dedup_key = ?", (key,)).fetchone()
        return old["id"], "doublon"  # l'événement d'origine, déjà au journal

def read(agent, *patterns):
    """Abonnement : les événements que cet agent n'a pas encore traités, dans l'ordre.
    Motifs au format LIKE : 'mail.casier.item', 'crm.deal.%', '%.error'."""
    where = " OR ".join("topic LIKE ?" for _ in patterns)
    with _connect() as db:
        row = db.execute("SELECT cursor FROM agents WHERE name = ?", (agent,)).fetchone()
        return db.execute(f"SELECT * FROM events WHERE ({where}) AND seq > ? ORDER BY seq",
                          (*patterns, row["cursor"] if row else 0)).fetchall()

def ack(agent, seq):
    """Après traitement : un agent redémarré reprend exactement où il s'était arrêté."""
    with _connect() as db:
        db.execute("INSERT INTO agents(name, cursor) VALUES (?, ?) ON CONFLICT(name)"
                   " DO UPDATE SET cursor = MAX(cursor, excluded.cursor)", (agent, seq))

def heartbeat(agent, interval_s=60, success=False, now=None):
    """Signal de vie : chaque agent l'appelle toutes les interval_s secondes
    (tâche APScheduler), et avec success=True après chaque tâche réussie."""
    now = now or time.time()
    with _connect() as db:
        db.execute(
            "INSERT INTO agents(name, interval_s, last_beat, last_success) VALUES (?,?,?,?)"
            " ON CONFLICT(name) DO UPDATE SET interval_s = excluded.interval_s,"
            " last_beat = excluded.last_beat,"
            " last_success = COALESCE(excluded.last_success, last_success)",
            (agent, interval_s, now, now if success else None))

def watchdog_tick(now=None):
    """Chien de garde, lancé chaque minute par FORGE et par le hub. Même émetteur et
    même clé : une seule alerte par panne, même avec deux gardiens."""
    now = now or time.time()
    with _connect() as db:
        prev = db.execute("SELECT last_beat FROM agents WHERE name = 'watchdog'").fetchone()
        silent = db.execute("SELECT name, last_beat FROM agents WHERE name != 'watchdog'"
                            " AND ? - last_beat > 2 * interval_s", (now,)).fetchall()
    heartbeat("watchdog", 60, now=now)
    if prev and now - prev["last_beat"] > 180:
        return []  # trou de plus de 3 min : la machine sortait de veille, un cycle de grâce
    alerts = []
    for name, last_beat in silent:
        late = now - last_beat
        topic, level = ("agent.down.critical", "critique") if late > 3600 else ("agent.down", "alerte")
        _, status = emit("watchdog", topic, f"{name} muet depuis {late / 60:.0f} min", level,
                         entities=[f"agent:{name}"], dedup_key=f"{name}:{last_beat:.0f}")
        if status == "nouveau":
            alerts.append((name, level))
    return alerts
```

`emit` ne renvoie jamais un résultat ambigu. Il répond `nouveau`, `doublon` (avec l'id de l'événement d'origine) ou `boucle`, et une boucle coupée laisse elle-même une trace `erreur` au journal. Quand un agent réagit à un événement, il en émet un nouveau avec le même `correlation_id`, `hops + 1` et une `dedup_key` tirée de l'id de l'événement source : rejouer l'événement ne produit rien de plus. Avant une action externe, comme envoyer un mail, l'agent publie son intention et n'agit que si `emit` répond `nouveau`. Un rejeu n'envoie donc jamais deux fois le même mail. Si un simple fichier ne suffit plus un jour, NATS ou Redis Streams prennent le relais avec le même contrat.

**Signaux de vie.** Chaque agent appelle `heartbeat()` dès son démarrage puis chaque minute (une tâche APScheduler), et avec `success=True` après chaque tâche réussie. `watchdog_tick()` tourne chaque minute à deux endroits : dans FORGE, et dans une boucle de quelques lignes que le hub lance en même temps que les agents. Si FORGE tombe, sa panne est donc signalée comme celle des autres. Un agent muet depuis plus de 2 minutes déclenche une `alerte`, depuis plus d'une heure une alerte `critique`. Chaque niveau n'est émis qu'une fois par panne, même avec deux gardiens, car ils partagent l'émetteur et la clé. À la sortie de veille, le chien de garde voit son propre trou et laisse une minute aux agents avant de juger. Les feux de santé du tableau de bord lisent directement la table `agents`, en SQL, quel que soit le langage de ton hub.

**2.2 Le branchement sur l'existant.** L'Agent Mail ne demande que trois ajouts :
- publier `mail.casier.item` (casier, expéditeur, objet, chemins des pièces jointes) à chaque message rangé ;
- accepter `mail.casier.create` et `mail.rule.create`, pour que les autres agents créent leurs casiers (*impôts*, *école*, *Prospects*) ;
- écrire son signal de vie dans la table `agents` (une requête SQL), pour apparaître dans les feux de santé.

Les casiers deviennent alors les files d'entrée de tout l'OS. Ils servent aussi de rangement universel : un agent peut y déposer un justificatif, un lead ou une PR à relire, sans nouvel écran à coder.

**2.3 Des clés communes.** Tous les agents désignent les choses avec les mêmes identifiants : `country:TW`, `isin:…`, `siren:…`, `domain:…`, `pkg:pypi/requests`, `course:S5-ECONOMETRIE`. Une table `entities` relie les alias : « TSMC », son ISIN et son ticker pointent vers la même ligne. VIGIE peut ainsi demander en une requête : « qui, chez toi, est exposé à Taïwan ? ».

Chaque donnée a **un seul propriétaire** : TRÉSOR pour les opérations et les positions, FILON pour les entreprises et les contacts, CURSUS pour les blocs de révision, FORGE pour le code des agents. Les autres lui envoient une demande au lieu d'écrire directement.

**2.4 Un contexte partagé.** Une ligne `context` donne le mode (normal, examens, voyage, vacances) et les heures calmes. CURSUS la règle pour tes partiels, l'Agent Mail pour tes voyages, toi par un interrupteur. Chaque agent la lit avant d'agir.

**2.5 Un client HTTP/LLM instrumenté.** Toutes les requêtes passent par la même couche, qui les note dans le journal : hôte, statut, latence, tokens, coût. Ta surveillance API actuelle couvre donc aussi les nouveaux agents. Cette couche applique le budget de chaque agent et envoie les données sensibles au modèle local.

**2.6 Autonomie graduée et garde-fous.** C'est ce qui permet de tout laisser tourner sans surveillance. Voici le manifeste de FILON :

```yaml
# agents/filon/manifest.yaml
fichiers: {lecture: ["~/Prospection", "~/hub/hub.db"], ecriture: ["~/Prospection"]}
web_public: lecture_seule        # crawl de sites : GET sans cookies ni identifiants
# seuls hôtes autorisés à recevoir des identifiants :
api: ["recherche-entreprises.api.gouv.fr", "api.insee.fr", "*.opendatasoft.com",
      "api.francetravail.io", "www.googleapis.com", "smtp.prospection.ton-domaine.fr"]
commandes: []                    # aucune commande système
budget_llm_eur_jour: 0.80
autonomie:
  reponse_dans_un_fil: {modeles_fixes: auto, texte_libre: validation}
  premier_contact: {auto_sous_plafond: 10/jour}   # au-delà → casier « À valider »
  suppression_de_donnees: validation
```

- **Le LLM propose, le code décide.** Le contenu du web et des mails est considéré comme non fiable. En autonomie, ce que renvoie le LLM n'est jamais exécuté : c'est un JSON, vérifié par `pydantic` puis comparé au manifeste. Une page piégée qui « demande » tes fichiers ne déclenche donc rien.
- **Aucun code écrit par un LLM ne s'exécute sans ta relecture.** La règle précédente vaut aussi pour FORGE, le seul agent qui touche au code. En autonomie, il ne répare que des données (sélecteurs CSS, correspondances de colonnes), qu'un extracteur fixe applique (voir 3.5). Un correctif qui exige du code est testé dans un conteneur sans réseau, puis t'attend en PR. Le diff y est annoté : nouveaux imports, appels réseau, accès aux fichiers.
- **Ce qui part en ton nom.** Dans un fil engagé, seuls des modèles fixes partent seuls : lien de réservation, relance courtoise, confirmation d'opposition. Un premier contact est rédigé par le LLM à partir des seules données publiques de l'entreprise et de ta présentation commerciale. Son contexte ne contient rien de confidentiel : il n'a donc rien à divulguer.
- **Secrets** : ils restent dans le trousseau de l'OS (`keyring`) et sont masqués dans les logs et les prompts.
- **Suppressions** : aucune donnée n'est effacée directement, tout passe 30 jours en quarantaine. Seuls les caches régénérables font exception : images Docker orphelines, `node_modules` avec lockfile.
- **Contrôle** : chaque agent a un bouton pause, un arrêt général coupe tout, et chaque action est tracée dans le journal.

## 3. Les cinq agents

### 3.1 TRÉSOR : le directeur financier qui clôture ton mois pendant que tu dors

**Nom de code et mission principale.** **TRÉSOR** tient à jour, sans aucune saisie de ta part, une image exacte de ton argent, présent et à venir. Chaque opération est classée, et chaque dépense qui appelle un justificatif y est rattachée. Chaque ETF est décomposé jusqu'à ses lignes. Chaque mois est clôturé dans ton tableau de bord.

*Ce qu'il apporte de nouveau :*
- il retrouve la facture de chaque dépense qui en demande une, à partir des casiers de l'Agent Mail ;
- il « transparise » tes ETF, c'est-à-dire qu'il montre ton exposition réelle par entreprise, pays et devise. Cela vaut aussi pour les ETF synthétiques du PEA, dont les titres détenus ne sont pas ceux de l'indice ;
- il prévoit ta trésorerie à 90 jours et voit venir les découverts avant ta banque.

**Capacités techniques requises**
- **Scripts Python** :
  - import des relevés : CSV/OFX avec `ofxtools`, PDF avec `pdfplumber`, factures Factur-X avec `factur-x`. Le format de chaque export (correspondance des colonnes) est décrit dans un YAML, pas dans le code ;
  - classement des opérations par règles YAML, puis par le modèle local pour le reste ;
  - rapprochement : montant exact, date à ±5 jours, nom du marchand comparé avec `rapidfuzz` ;
  - détection des abonnements, hausses, doublons et débits inhabituels ;
  - calculs `pandas`/DuckDB : patrimoine net, taux d'épargne, rendement XIRR de tes versements, écart à l'allocation cible ;
  - **transparisation**, selon le mode de réplication de chaque ETF, lu sur sa fiche et noté dans `positions.yaml` :
    - ETF **physique** : le fichier de positions publié par l'émetteur ;
    - ETF **synthétique**, ce qui est le cas de tout ETF PEA sur un indice hors Europe (Monde, S&P 500, Émergents), car le PEA impose 75 % d'actions européennes. Le fonds détient alors un panier d'actions européennes et reçoit la performance de l'indice par un swap. Ses positions publiées ne disent donc rien de ton exposition. TRÉSOR prend la composition de l'indice suivi : pondérations par pays et principales lignes de la fiche mensuelle du fournisseur d'indice, ou, ligne à ligne, positions d'un ETF physique qui suit le même indice. Le panier détenu s'affiche à part, comme collatéral, avec le risque de contrepartie du swap, que la réglementation OPCVM plafonne à 10 % de l'actif du fonds ;
  - projection de trésorerie ;
  - écriture du classeur Budget avec `openpyxl` (Excel) ou `gspread` (Google Sheets).
- **Fichiers** : casiers *banque*, *factures* et *impôts* ; grand livre `finances.duckdb` ; justificatifs renommés (`Finances/Justificatifs/2026/09/2026-09-12_Operateur_29,99.pdf`) ; `positions.yaml` (ISIN, quantités, enveloppe, cible, mode de réplication, indice suivi) tant qu'aucune API courtier n'est branchée.
- **Réseau** :
  - banque : un agrégateur DSP2 en lecture seule, par exemple Enable Banking (conditions d'usage personnel à vérifier). La réauthentification exigée tous les 180 jours est rappelée 7 jours avant ;
  - courtier : le Flex Web Service si tu es chez Interactive Brokers ; sinon, les exports CSV et les avis d'opéré rangés dans les casiers ;
  - cours de bourse via `yfinance` (suffixe `.PA` pour Euronext Paris), avec une source de secours ;
  - taux de change de la Banque centrale européenne ;
  - fichiers de positions des émetteurs (iShares, Amundi, Xtrackers…) pour les ETF physiques ; fiches des fournisseurs d'indices (MSCI, S&P) pour les synthétiques ;
  - Playwright en session persistante, pour récupérer une facture sur un espace client sans double authentification.
- **IA** : extraction et classement en local. **Aucun montant ne vient du LLM** : le code calcule, et chaque montant extrait est recoupé entre la facture et l'opération.
- **Branché sur** : reçoit `mail.casier.item`, `crm.deal.*`, `veille.signal`. Publie `finance.exposure.updated`, `finance.cashflow.alert`, `finance.anomaly`, `finance.receivable.late`, `finance.month.closed`.

**Scénario d'usage (Day in the life) : la clôture de septembre, le 2 octobre à 05:30**
1. TRÉSOR récupère les 148 opérations de septembre, par l'API DSP2 ou, en V0, depuis le relevé rangé dans *banque*. Les règles en classent 139, le modèle local les 9 autres.
2. 41 débits appellent un justificatif : achats en ligne, abonnements, énergie, télécom, assurances. 35 retrouvent leur facture dans *factures*. Pour 4 autres, il télécharge le PDF sur l'espace client du fournisseur. Les 2 restants vont dans le casier *Justificatifs manquants*.
3. Il repère trois anomalies :
   - ton assurance habitation augmente de 17 % à l'échéance. Il prépare en brouillon la résiliation, possible à tout moment après un an grâce à la loi Hamon, et deux demandes de devis ;
   - deux abonnements de streaming sont facturés en double depuis août ;
   - des frais de tenue de compte sont réapparus.
4. Il écrit l'onglet « 2026-09 » du classeur Budget et archive un PDF de synthèse.
5. Il recalcule ton exposition réelle. Ta poche Émergents, logée dans ton PEA, est un ETF synthétique : TRÉSOR applique donc les pondérations de l'indice MSCI Emerging Markets, pas celles du panier européen que détient le fonds. Taïwan pèse environ 19 % de l'indice et TSMC environ 10,6 %. Ta poche de 16 % te donne donc une exposition réelle de 3,0 % à Taïwan, dont 1,7 % à TSMC. Le dollar pèse 60 % de l'ensemble. La poche Émergents est à 16 % pour une cible de 20 % : TRÉSOR affecte tout ton versement programmé du 5 (500 €) à l'ETF Émergents et prépare le ticket d'ordre. Rééquilibrer sans vendre évite les frais de cession et, hors PEA, l'impôt sur la plus-value.
6. Il projette ta trésorerie. L'assurance auto (le 18), puis le prélèvement d'impôt annoncé dans *impôts* (le 20), feront passer ton compte sous 150 €. Il t'alerte 18 jours avant, avec le virement à faire depuis ton livret.
7. Il publie `finance.exposure.updated`, et VIGIE remonte Taïwan dans sa liste de surveillance.

À ton réveil, le mois est clôturé et trois décisions sont prêtes, sans aucune saisie de ta part. Un seul geste reste manuel, par choix : passer l'ordre. Il n'est automatisable que chez un courtier doté d'une API, et sous plafond.

**Intégration UI**

### 3.5 FORGE : l'ingénieur d'astreinte de ta machine et de tes agents

**Nom de code et mission principale.** **FORGE** garde ton environnement de développement propre, sûr et sauvegardé. Surtout, il **répare les autres agents quand ils tombent en panne**, la nuit, avant que tu t'en aperçoives.

*Ce qu'il apporte de nouveau :* il répare seul un collecteur cassé par un changement de site, en réécrivant sa configuration et jamais son code, puis rejoue la tâche manquée. Il sauvegarde aussi chaque soir ton travail non commité, sans toucher à tes dépôts.

**Capacités techniques requises**
- **Scripts** :
  - superviseur : `watchdog_tick()` du noyau, redémarrage avec un délai croissant, erreurs regroupées par empreinte (type d'exception + fichier + ligne) ;
  - **auto-réparation par la configuration** : les collecteurs sont déclaratifs (sélecteurs CSS pour les sites, correspondances de colonnes pour les exports), lus par un extracteur commun que le LLM ne modifie jamais. Quand une source casse, le LLM propose une nouvelle configuration en JSON. Le code la vérifie (ci-dessous), la déploie et rejoue la tâche. Tout correctif qui exige du code devient une PR à relire ;
  - audit des dépendances de tous tes dépôts (`osv-scanner`, `pip-audit`, `npm audit`), avec branche, tests et PR ;
  - `gitleaks` avant chaque push, pour bloquer les secrets ;
  - sauvegarde du travail non commité ;
  - entretien de la machine (`psutil`) : disque, ports, process oubliés, caches régénérables ;
  - sauvegardes `restic`, avec un **test de restauration** chaque mois ;
  - suivi des coûts API par agent.

Voici ce que le LLM peut renvoyer pour réparer une source, et ce que le code vérifie avant tout déploiement. Testé : une bonne proposition passe. Sont refusés : un champ `url` ou `code` en plus, une réponse en Python, un CSS invalide, des sélecteurs qui visent le menu, des liens qui sortent du site, des articles connus introuvables.

```python
# noyau/reparation.py — la seule chose que le LLM peut changer seul : des sélecteurs
from urllib.parse import urljoin, urlparse
from parsel import Selector
from pydantic import BaseModel, ConfigDict

class Selecteurs(BaseModel):
    model_config = ConfigDict(extra="forbid")  # un champ de plus (url, code, commande…) → rejet
    article: str  # un bloc par article, ex. "article.card"
    titre: str    # ex. "h3 a::text"
    lien: str     # ex. "h3 a::attr(href)"
    date: str     # ex. "time::attr(datetime)"

def verifier(reponse_llm, page, url_source, titres_connus, minimum=5):
    """Le LLM propose, ce code décide. Renvoie (sélecteurs, []) ou (None, motifs du refus)."""
    try:
        s = Selecteurs.model_validate_json(reponse_llm)
        items = [{k: " ".join((b.css(getattr(s, k)).get() or "").split())
                  for k in ("titre", "lien", "date")}
                 for b in Selector(text=page).css(s.article)]  # du CSS : ni disque, ni réseau
    except Exception as e:
        return None, [f"proposition invalide : {e}"]
    hote = urlparse(url_source).hostname.removeprefix("www.")
    motifs = []
    if len(items) < minimum or not all(all(i.values()) for i in items):
        motifs.append("trop peu d'articles complets")
    if any((urlparse(urljoin(url_source, i["lien"])).hostname or "").removeprefix("www.") != hote
           for i in items):
        motifs.append("lien hors du site source")
    connus = {" ".join(t.split()) for t in titres_connus}
    if len(connus & {i["titre"] for i in items}) < min(minimum, len(connus)):
        motifs.append("articles déjà connus introuvables")
    return (None, motifs) if motifs else (s, [])
```

Un sélecteur CSS ne fait que choisir des morceaux d'une page déjà téléchargée : il ne peut ni lire un fichier, ni ouvrir une connexion. L'URL de la source, écrite par toi, n'est pas dans le schéma, donc le LLM ne peut pas la changer.

- **Fichiers et OS** : lecture de `~/dev`. L'écriture autonome se limite aux configurations des sources, versionnées et annulables en un clic. Le code des agents n'est modifié que dans des branches `forge/*`, que toi seul fusionnes. Dossier `.forge/fixtures/` (dernières pages et sorties valides de chaque collecteur) ; tests de code dans un conteneur Docker sans réseau ; supervision des process.
- **Réseau** : GitHub ou GitLab (PR, issues, intégration continue) ; OSV.dev ; registres PyPI et npm ; cible de sauvegarde (NAS, S3, B2) ; LLM.
- **Branché sur** : reçoit tous les `%.error`, les `agent.down%` et les échecs de validation. Publie `dev.incident.*` (nouveau → en réparation → réparé ou escaladé), `dev.dependencies.updated` (pour que VIGIE surveille tes paquets) et `dev.budget.exceeded`. Le chien de garde tourne aussi dans le hub : si FORGE tombe, sa panne est signalée comme celle des autres.

**Scénario d'usage (Day in the life) : la nuit de jeudi à vendredi**
1. **03:10.** Le collecteur VIGIE d'un think tank renvoie 0 article trois fois de suite, car le site a changé son HTML. Un événement `vigie.collector.error` part, avec l'empreinte `vigie.collector.thinktank:SelectorEmpty`.
2. FORGE récupère la page actuelle et demande au LLM de nouveaux sélecteurs pour cette source. La page est un contenu non fiable, qui pourrait cacher des instructions piégées. Peu importe : la seule réponse acceptée est un JSON de quatre sélecteurs CSS. S'il contient en plus une URL, du code ou une commande, la proposition est rejetée.
3. Il vérifie les sélecteurs hors réseau, sur la copie de la page : 14 articles avec titre, lien et date, et tous les liens restent sur le site. Les 10 derniers articles déjà archivés par VIGIE sont tous retrouvés, preuve que les sélecteurs visent les bons blocs.
4. Les vérifications passent. FORGE enregistre la nouvelle configuration (l'ancienne reste restaurable en un clic), relance le collecteur et rejoue la tâche. VIGIE termine son brief avant 07:00. Si une vérification avait échoué, ou si le site exigeait du code nouveau (un rendu JavaScript, par exemple), rien n'aurait été déployé. L'incident serait remonté avec la page, la proposition et, le cas échéant, une PR à relire.
5. La même nuit, FORGE traite trois autres sujets :
   - **une faille** signalée par OSV dans deux projets. Il crée une branche de mise à jour et lance les tests : la PR est prête pour l'un ; pour l'autre, les tests échouent et une issue est ouverte avec le log ;
   - **du travail non commité** depuis 48 h dans deux dépôts. FORGE crée un commit à partir d'un index temporaire, ce qui laisse ton index et tes fichiers intacts. Il le vérifie avec `gitleaks`, puis le pousse sur une référence `refs/forge/wip/…` d'un dépôt de sauvegarde privé, jamais sur un dépôt public ;
   - **le disque** : 31 Go libérés (images Docker orphelines, `node_modules` reconstructibles de projets inactifs depuis 90 jours).

À 07:00, la carte FORGE affiche : « 1 auto-réparation, 1 PR prête, 1 issue, 2 sauvegardes, 31 Go libérés, 6 agents sur 6 au vert ».

**Intégration UI**
- **Feux de santé** en haut du tableau de bord : un voyant par agent, lu dans la table `agents`, avec le dernier signal, le dernier succès, la prochaine exécution, le coût du jour et un bouton pause.

- **Casiers et journal** : casiers *Incidents* et *PR à relire*. Les erreurs répétées deviennent une seule ligne enrichie, par exemple : `FORGE · erreur → réparé · vigie.collector.thinktank (3 occurrences)`.
- **Notifications** : seulement ce qu'il n'a pas su réparer. Une alerte si une réparation échoue à ses vérifications, un push critique si un agent reste muet plus d'une heure.

**Dès aujourd'hui (V0)** : signaux de vie et chien de garde (déjà dans le noyau), regroupement des erreurs et scan nocturne des dépôts (non commité, non poussé, OSV) → feux de santé et widget *Dépôts*. Dès maintenant, écris tes collecteurs HTML en déclaratif (une URL et des sélecteurs dans un YAML). Fais-leur aussi enregistrer leurs pages et sorties valides dans `.forge/fixtures/`. C'est ce qui rendra l'auto-réparation (V1) à la fois possible et sûre.

## 4. Synergie : les points de contact, testés

### 4.1 Quatre chaînes qui traversent plusieurs agents

- **Signal → euros → argumentaire.** VIGIE détecte, TRÉSOR chiffre, FILON annote. Le tableau de bord n'affiche qu'une carte, avec une sous-ligne par agent (voir le scénario 3.2). Le chiffrage repose sur l'exposition réelle, calculée sur l'indice suivi quand l'ETF est synthétique.
- **Facture impayée.** FILON passe une affaire en « Gagné » et transmet le montant et l'échéance ; TRÉSOR guette le virement. Le lendemain de l'échéance, sans paiement, TRÉSOR publie `finance.receivable.late`, et FILON envoie une relance courtoise dans le fil (un modèle fixe). À J+15, une relance ferme attend ta validation dans *À valider*. Elle rappelle les pénalités de retard et l'indemnité forfaitaire de 40 € pour frais de recouvrement.
- **Semaine de partiels.** CURSUS passe le contexte en « examens », et chaque agent s'adapte :
  - FILON descend à 3 premiers contacts par jour et ferme ses créneaux ;
  - VIGIE passe à un résumé quotidien ;
  - TRÉSOR ne notifie que le critique ;
  - FORGE reporte les mises à jour non urgentes.
- **Panne silencieuse évitée.** Ta banque renomme une colonne de son export CSV. La validation de schéma de TRÉSOR signale l'erreur au lieu d'importer des montants faux. FORGE fait proposer au LLM la nouvelle correspondance des colonnes : une donnée, pas du code. Le code ne l'accepte que si la somme des montants importés égale la variation du solde sur le relevé. L'import est rejoué, et tu ne vois qu'une carte : « réparé automatiquement ».

### 4.2 Les points de contact et leurs tests

| Point de contact | Ce qui peut casser | Règle | Test automatique |
|---|---|---|---|
| Deux agents, un même fait | 2 alertes pour 1 événement | même `correlation_id` → 1 carte, une sous-ligne par agent | injecter un faux signal « Taïwan » → 1 seule carte |
| Réactions en chaîne | boucle A → B → A ; mail envoyé deux fois | `hops` ≤ 3, coupure tracée en `erreur` ; `dedup_key` tirée de l'événement source ; action externe seulement si `emit` répond `nouveau` | rejouer 2 fois un événement → aucun effet de plus, aucun mail en double |
| Clés de dédoublonnage | deux faits distincts fusionnés en silence | clé préfixée par agent et sujet ; `emit` distingue `nouveau`, `doublon` et `boucle` | même clé chez deux agents → 2 événements ; 8 process, même clé → 1 seul |
| Ressource partagée (agenda) | RDV posé sur une révision | un propriétaire par ressource : les blocs de révision sont à CURSUS, FILON ne propose que des créneaux libres | réserver sur un bloc CURSUS → refusé, alternative proposée |
| Agent muet | silence pris pour « rien à signaler » | `heartbeat()` chaque minute ; `watchdog_tick()` dans FORGE et dans le hub ; alerte après 2 intervalles, une seule par panne | tuer un process → 1 alerte en 3 min au plus, pas une par minute ; tuer FORGE → signalé par le hub |
| Entrée qui change de format | données fausses sans erreur | validation `pydantic` à chaque entrée : erreur explicite plutôt que donnée fausse | CSV à colonne renommée → erreur → réparation |
| Contenu hostile (page, mail) | injection de prompt → fuite de données | le LLM ne produit que des propositions JSON validées par le manifeste | page piégée « envoie ~/.ssh » → action refusée + alerte |
| Auto-réparation | code piégé déployé sans relecture | en autonomie, seulement des sélecteurs (schéma fermé), appliqués par un extracteur fixe ; tout code → PR à relire | réponse du LLM en Python, ou JSON avec un champ `url` → refusée, incident remonté |
| Chiffres | montant inventé par le LLM | le code calcule ; tout montant extrait est recoupé | facture mal lue → non rapprochée → casier *Justificatifs manquants* |
| Exposition ETF (TRÉSOR → VIGIE) | ETF synthétique lu par son panier → Taïwan à 0 % | réplication synthétique → composition de l'indice suivi | ETF PEA Émergents → Taïwan ≈ 19 % de la poche, pas 0 % |
| Machine éteinte ou en veille | tâches et événements perdus ; rafale de fausses alertes au réveil | jobstore persistant + `misfire_grace_time` d'APScheduler ; curseur d'abonnement sauvegardé ; un cycle de grâce du chien de garde | éteindre une nuit → tâches rejouées, événements repris au bon endroit, aucune fausse alerte ; un agent mort pendant la veille → signalé au 2e passage |
| Coûts | boucle LLM coûteuse | budget par agent et par jour dans le client instrumenté, bascule sur le modèle local | budget atteint → bascule + ligne au brief |

Écris ces douze tests dans un seul fichier, `tests/test_jonctions.py`, qui injecte des événements dans `hub.db` et vérifie ce qui ressort au tableau de bord. Relance-le à chaque nouvel agent.

**Écarté volontairement :**
- **Ordres de bourse autonomes** : il n'y a qu'un ordre par mois à gagner, pour un risque maximal. Le ticket prêt suffit.
- **Correctifs de code fusionnés sans relecture** : le gain serait de quelques heures sur une source en panne, pour un risque d'exécuter du code piégé. La réparation autonome se limite aux sélecteurs et aux correspondances de colonnes.
- **Scraping de LinkedIn** : interdit par ses conditions d'utilisation, et moins riche que l'open data française.
- **Microservices, Kubernetes, serveur de messages** : SQLite suffit pour un seul utilisateur, et le contrat d'événement permet de migrer plus tard sans rien réécrire.
- **Nouvelle interface** : les casiers, le journal et quelques widgets réutilisent ce que ton hub sait déjà afficher.
