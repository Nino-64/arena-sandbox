# Ton hub devient un OS personnel : 5 agents et le noyau qui les relie

Ton hub a déjà les deux pièces maîtresses d'un OS personnel : des **casiers**, où l'information arrive triée, et un **journal d'événements en temps réel**. J'en fais le système nerveux de l'ensemble. Les cinq agents ci-dessous sont des blocs indépendants : ils lisent les casiers, écrivent dans le journal et se parlent à travers lui. Pour chacun, tu trouveras la vision complète, puis ce que tu peux en coder dès aujourd'hui.

Si ton journal a son propre stockage, un petit adaptateur fait le pont. |

## 2. Le noyau (à coder en premier, environ une demi-journée)

Le noyau n'est pas un agent, c'est le code commun. Chaque agent est un process Python doté de trois éléments :
- un **manifeste**, qui fixe ses droits ;
- des **tâches planifiées** : APScheduler avec un stockage SQLite des tâches (jobstore), pour rattraper au démarrage ce qui a été manqué ;
- des **abonnements** à des sujets du journal.

**2.1 Un seul contrat d'événement.** Le journal sert à la fois d'écran de contrôle, de bus entre agents et de registre d'audit. Chaque événement porte six champs clés :
- `topic`, de la forme `domaine.objet.verbe` (ex. `finance.exposure.updated`) ;
- `severity`, le niveau de l'événement (voir 2.7) ;
- `entities`, les objets concernés (voir 2.3) ;
- `dedup_key`, pour qu'un événement ne soit traité qu'une fois ;
- `correlation_id` : tous les événements nés d'un même fait réel partagent cet identifiant ;
- `hops`, un compteur qui coupe les boucles.

Version minimale, testée :

```python
# noyau/bus.py — journal + bus partagé : un fichier SQLite, zéro serveur
import json, sqlite3, time, uuid
from contextlib import closing

DB_PATH = "hub.db"

def _connect():
    # une connexion par appel : sûr depuis plusieurs threads et plusieurs process
    return closing(sqlite3.connect(DB_PATH, isolation_level=None, timeout=10))

with _connect() as db:
    db.execute("PRAGMA journal_mode=WAL")  # lectures possibles pendant les écritures
    db.execute("""CREATE TABLE IF NOT EXISTS events(
      seq INTEGER PRIMARY KEY AUTOINCREMENT, id TEXT, ts REAL, agent TEXT,
      topic TEXT, severity TEXT, title TEXT, entities TEXT, payload TEXT,
      dedup_key TEXT UNIQUE, correlation_id TEXT, hops INTEGER)""")

def emit(agent, topic, title, severity="info", entities=(), payload=None,
         dedup_key=None, correlation_id=None, hops=0):
    """Publie un événement. Renvoie son id, ou None (doublon ou boucle)."""
    if hops > 3:                                   # coupe-circuit anti-boucle
        return None
    eid = uuid.uuid4().hex
    with _connect() as db:
        cur = db.execute(
            "INSERT OR IGNORE INTO events(id, ts, agent, topic, severity, title,"
            " entities, payload, dedup_key, correlation_id, hops)"
            " VALUES (?,?,?,?,?,?,?,?,?,?,?)",
            (eid, time.time(), agent, topic, severity, title,
             json.dumps(list(entities)),
             json.dumps(payload or {}, ensure_ascii=False),
             dedup_key, correlation_id or eid, hops))
        return eid if cur.rowcount else None

def read(topic_prefix, after_seq=0):
    """Abonnement par polling : chaque agent mémorise le dernier seq traité."""
    with _connect() as db:
        return db.execute(
            "SELECT * FROM events WHERE topic LIKE ? AND seq > ? ORDER BY seq",
            (topic_prefix + "%", after_seq)).fetchall()
```

Quand un agent réagit à un événement, il en émet un nouveau avec le même `correlation_id` et `hops + 1`. Si un simple fichier ne suffit plus un jour, NATS ou Redis Streams le remplacent sans changer le contrat.

**2.2 Le branchement sur l'existant.** L'Agent Mail ne demande qu'une modification. Il publie `mail.casier.item` (casier, expéditeur, objet, chemins des pièces jointes) à chaque message rangé. Il accepte aussi `mail.casier.create` et `mail.rule.create`, pour que les autres agents créent leurs casiers (*impôts*, *école*, *Prospects*). Les casiers deviennent ainsi les files d'entrée de tout l'OS. Ils deviennent aussi un contenant universel : un agent peut y déposer un justificatif, un lead ou une PR à relire, sans nouvel écran à coder.

**2.3 Des clés communes.** Tous les agents désignent les choses avec les mêmes identifiants : `country:TW`, `isin:…`, `siren:…`, `domain:…`, `pkg:pypi/requests`, `course:S5-ECONOMETRIE`. Une table `entities` relie les alias : « TSMC », son ISIN et son ticker renvoient à la même ligne. VIGIE peut ainsi demander en une seule requête : « qui, chez toi, est exposé à Taïwan ? ». Chaque donnée a **un seul propriétaire** :
- TRÉSOR : opérations et positions ;
- FILON : entreprises et contacts ;
- CURSUS : blocs de révision ;
- FORGE : code des agents.

Les autres agents ne modifient jamais ces données directement : ils envoient une demande au propriétaire.

**2.4 Un contexte partagé.** Une ligne `context` contient le mode (normal, examens, voyage, vacances) et les heures calmes. CURSUS la règle pour les partiels, l'Agent Mail pour les voyages, et toi par un interrupteur. Chaque agent la lit avant d'agir.

**2.5 Un client HTTP/LLM instrumenté.** Tous les agents passent leurs requêtes HTTP et LLM par la même couche. Elle note chaque requête dans le journal : hôte, statut, latence, tokens, coût. Ta surveillance API actuelle couvre donc aussi les nouveaux agents. Cette couche applique en plus le budget de chaque agent et envoie les données sensibles au modèle local.

**2.6 Autonomie graduée et garde-fous.** C'est ce qui permet de tout laisser tourner sans surveillance. Voici le manifeste de FILON :

```yaml
# agents/filon/manifest.yaml
fichiers: {lecture: ["~/Prospection", "~/hub/hub.db"], ecriture: ["~/Prospection"]}
web_public: lecture_seule        # crawl de sites : GET sans cookies ni identifiants
api: ["recherche-entreprises.api.gouv.fr", "api.insee.fr", "*.opendatasoft.com",
      "api.francetravail.io", "www.googleapis.com"]   # seuls hôtes qui reçoivent des identifiants
commandes: []                    # aucune commande système
budget_llm_eur_jour: 0.80
autonomie:
  reponse_dans_un_fil_engage: auto
  premier_contact: {auto_sous_plafond: 10/jour}   # au-delà → casier « À valider »
  suppression_de_donnees: validation
```

- **Le LLM propose, le code décide.** Le contenu du web et des mails est considéré comme non fiable. Le LLM ne renvoie que des propositions en JSON. Le code les vérifie avec `pydantic`, puis les compare au manifeste. Une page piégée qui « demande » tes fichiers ne déclenche donc rien.
- **Secrets** : ils restent dans le trousseau de l'OS (`keyring`) et sont masqués dans les logs et les prompts.
- **Aucune suppression directe** de tes données : elles passent 30 jours en quarantaine. Seuls les caches régénérables échappent à cette règle (images Docker orphelines, `node_modules` avec lockfile).
- **Exécution** : les correctifs de code sont testés dans un conteneur sans réseau. Chaque agent a un bouton pause, il existe un arrêt général, et chaque action est tracée dans le journal.

**2.7 La remontée dans ton tableau de bord.**

| Niveau | Exemples | Où ça apparaît |
|---|---|---|
| `info` | tâche terminée, 148 opérations importées | journal |
| `brief` | 10 leads du jour, note de veille | journal + badge du widget + brief du matin |
| `alerte` | abonnement en double, signal d'impact modéré, réponse positive d'un prospect | toast dans le hub + panneau *Alertes* |
| `critique` | débit suspect, rendu non commencé à J-2, agent arrêté depuis plus d'une heure | notification système + push sur le téléphone |
| `erreur` | exception d'un agent | journal, regroupée par FORGE ; passe en `alerte` si l'auto-réparation échoue |

## 3. Les cinq agents

### 3.1 TRÉSOR : le directeur financier qui clôture ton mois pendant que tu dors

**Nom de code et mission principale.** **TRÉSOR** tient à jour une image exacte de ton argent, présent et à venir, sans aucune saisie. Chaque opération est classée et rattachée à son justificatif. Chaque ETF est décomposé jusqu'à ses lignes. Chaque mois est clôturé dans ton tableau de bord.

*Ce qu'il apporte de nouveau :*
- il rapproche chaque opération de sa facture, à partir des casiers de l'Agent Mail ;
- il décompose tes ETF ligne par ligne (*transparisation*) pour montrer ton exposition réelle par entreprise, pays et devise ;
- il prévoit ta trésorerie à 90 jours et voit venir les découverts avant ta banque.

**Capacités techniques requises**
- **Scripts Python** :
  - import des relevés : CSV/OFX avec `ofxtools`, PDF avec `pdfplumber`, factures Factur-X avec `factur-x` ;
  - classement des opérations : règles YAML d'abord, modèle local pour le reste ;
  - rapprochement : montant exact, date à ±5 jours, nom du marchand comparé avec `rapidfuzz` ;
  - détection des abonnements, hausses de prix, doublons et débits inhabituels ;
  - calculs `pandas`/DuckDB : patrimoine net, taux d'épargne, rendement XIRR (le rendement réel compte tenu des dates de tes versements), écart à l'allocation cible, transparisation ;
  - projection de trésorerie ;
  - écriture du classeur Budget avec `openpyxl` (Excel) ou `gspread` (Google Sheets).
- **Fichiers** :
  - casiers *banque*, *factures*, *impôts* ;
  - grand livre `finances.duckdb` ;
  - justificatifs renommés, par exemple `Finances/Justificatifs/2026/09/2026-09-12_Operateur_29,99.pdf` ;
  - `positions.yaml` (ISIN, quantités, enveloppe, cible), tant qu'aucune API courtier n'est branchée.
- **Réseau** :
  - banque : un agrégateur DSP2 en lecture seule, par exemple Enable Banking (vérifie ses conditions d'usage personnel). La DSP2 impose une réauthentification tous les 180 jours ; TRÉSOR te la rappelle 7 jours avant ;
  - courtier : Flex Web Service chez Interactive Brokers, sinon les exports CSV et les avis d'opéré rangés dans les casiers ;
  - cours via `yfinance` (suffixe `.PA` pour Euronext Paris), avec une source de secours ;
  - taux de change de la Banque centrale européenne ;
  - compositions publiées par les émetteurs d'ETF (iShares, Amundi, Xtrackers…) ;
  - Playwright en session persistante, pour récupérer une facture sur un espace client sans double authentification.
- **IA** : extraction et classement en local. **Aucun montant ne vient du LLM** : le code calcule, et chaque montant extrait est recoupé entre facture et opération.
- **Branché sur** :
  - reçoit `mail.casier.item`, `crm.deal.*`, `veille.signal` ;
  - publie `finance.exposure.updated`, `finance.cashflow.alert`, `finance.anomaly`, `finance.receivable.late`, `finance.month.closed`.

**Scénario d'usage (Day in the life) : la clôture de septembre, le 2 octobre à 05:30**
1. TRÉSOR récupère les 148 opérations de septembre, par l'API DSP2 ou, en V0, depuis le relevé rangé dans *banque*. Les règles en classent 139, le modèle local les 9 autres.
2. Sur 127 débits, 121 retrouvent leur facture dans *factures*. Pour 4 autres, TRÉSOR télécharge le PDF sur l'espace client du fournisseur. Les 2 restants vont dans le casier *Justificatifs manquants*.
3. Il repère trois anomalies :
   - ton assurance habitation augmente de 17 % à l'échéance. Il prépare en brouillon une résiliation, possible à tout moment après un an grâce à la loi Hamon, et deux demandes de devis ;
   - deux abonnements de streaming sont facturés en double depuis août ;
   - des frais de tenue de compte sont réapparus.
4. Il écrit l'onglet « 2026-09 » du classeur Budget et archive un PDF de synthèse.
5. Il recalcule ton exposition réelle, par exemple : Taïwan 3,0 % dont TSMC 1,7 %, dollar 60 %. Ta poche Émergents est à 16 % pour une cible de 20 %. Il affecte donc tout ton versement programmé du 5 (500 €) à l'ETF Émergents et prépare le ticket d'ordre. Rééquilibrer sans vendre évite les frais de cession et, hors PEA, l'impôt sur la plus-value.
6. Il projette ta trésorerie. L'assurance auto (le 18), puis le prélèvement d'impôt annoncé dans *impôts* (le 20), feront passer ton compte sous 150 €. Il t'alerte 18 jours avant et t'indique le virement à faire depuis ton livret.
7. Il publie `finance.exposure.updated`, et VIGIE remonte Taïwan dans sa surveillance.

À ton réveil, le mois est clôturé et trois décisions t'attendent, toutes préparées, sans aucune saisie de ta part. Un seul geste reste manuel, par choix : passer l'ordre. Il n'est automatisable que chez un courtier doté d'une API, et sous un plafond.

**Intégration UI**
- **Module « Finances »**, sur le modèle de l'Agent Mail, avec quatre onglets : Mois · Portefeuille · Prévision · Justificatifs.
- **Widgets** :
  - *Patrimoine net* (courbe sur 12 mois) ;
  - *Trésorerie J+90* (solde projeté, zone rouge sous ton seuil) ;
  - *Allocation vs cible* ;
  - *Exposition réelle* ;
  - *Rapprochement* (125/127 débits justifiés).
- **Casiers et journal** : casiers *Justificatifs manquants* et *À résilier*. Exemple de ligne : `TRÉSOR · alerte · Abonnement facturé en double (2 × 13,49 €)`.
- **Notifications** :
  - un toast pour les décisions du mois ;
  - un push immédiat pour un débit inhabituel : marchand inconnu au-delà de 300 €, ou montant trois fois supérieur à l'habitude.

**Dès aujourd'hui (V0)** :
- relevé du casier *banque* + casier *factures* → classement, rapprochement, onglet du mois ;
- `positions.yaml` + cours du soir → widget *Allocation vs cible*.

### 3.2 VIGIE : la veille qui ne te parle que de ce qui te touche

**Nom de code et mission principale.** **VIGIE** lit le monde à ta place, dans les sources internationales et officielles, en langue originale. Il ne te remonte que ce qui touche **tes** expositions :
- ce que tu possèdes (via TRÉSOR) ;
- ceux à qui tu vends (via FILON) ;
- ce que ton code utilise (via FORGE) ;
- là où tu vas (casier *voyages*).

Chaque signal arrive avec sa source primaire et un niveau de confiance.

*Ce qu'il apporte de nouveau :*
- l'importance d'une nouvelle se mesure par rapport à toi : intensité × exposition ;
- une escalade se repère par anomalie statistique, pas par mot-clé ;
- VIGIE **note ses propres prédictions**, pour savoir quelles sources sont fiables.

**Capacités techniques requises**
- **Scripts** :
  - flux RSS choisis (`feedparser`) : ministères, banques centrales, think tanks, presse spécialisée ;
  - API GDELT DOC 2.0 : presse mondiale mise à jour toutes les 15 minutes, avec volumes et tonalité par thème et par pays ;
  - extraction du texte avec `trafilatura`, et Playwright pour les sites en JavaScript ;
  - traduction, puis regroupement des articles en événements (vecteurs sémantiques + seuil de similarité) ;
  - entités rattachées aux clés communes ;
  - détection d'escalade : écart à la moyenne mobile sur 30 jours, mesuré en écarts-types ;
  - détection des changements sur des pages surveillées ;
  - prévisions datées, notées ensuite avec le score de Brier.
- **Fichiers** :
  - archive locale des articles retenus (Markdown + index vectoriel `sqlite-vec`) : ta base de renseignement privée ;
  - `watchlist.yaml` (thèmes, pays, pages) ;
  - briefs archivés.
- **Réseau** :
  - flux RSS et pages web, GDELT ;
  - liste consolidée des sanctions de l'UE et liste OFAC ;
  - Journal officiel via l'API Légifrance (portail PISTE) ;
  - « Conseils aux voyageurs » de France Diplomatie ;
  - séries de la BCE et de FRED ;
  - en option, collecte 24 h/24 sur un VPS.
- **IA** : regroupement, traduction, synthèse. Une affirmation sans source est marquée « non confirmé ».
- **Branché sur** :
  - reçoit `finance.exposure.updated`, `crm.account.updated`, `dev.dependencies.updated`, `mail.casier.item` (voyages) ;
  - publie `veille.signal` (impact + entités), `veille.brief.ready`, `veille.page.changed`.

**Scénario d'usage (Day in the life) : mardi, 05:50**
1. Le volume d'articles GDELT qui associent Taïwan à « exercices militaires / blocus » monte à 4,2 écarts-types au-dessus de sa moyenne sur 30 jours.
2. VIGIE regroupe 37 articles en 9 langues en un seul événement et traduit les sources chinoises et taïwanaises. Il retrouve la source primaire, un communiqué du ministère taïwanais de la Défense, et marque l'événement « confirmé ».
3. Il interroge les clés communes :
   - TRÉSOR indique 3,0 % du portefeuille exposé à Taïwan, dont TSMC 1,7 % ;
   - FILON a deux comptes qui importent de l'électronique d'Asie ;
   - aucun voyage n'est prévu dans la zone.
4. L'impact est modéré. VIGIE demande un stress test à TRÉSOR : un recul de 20 % des actions taïwanaises coûterait 0,6 % du portefeuille.
5. Il rédige une note de six lignes : faits confirmés, inconnues, et trois indicateurs à suivre (NOTAM et avertissements de navigation, primes d'assurance maritime, ouverture de la Bourse de Taipei). Il ajoute une ligne de contexte aux deux fiches FILON. Il enregistre aussi une prévision datée, marquée comme estimation (« blocus effectif sous 30 jours : 7 % »), qu'il notera dans 30 jours.
6. À 07:00, l'événement ouvre le brief et s'affiche en orange dans le Radar, avec son impact chiffré. Ensuite, VIGIE suit les indicateurs sans te déranger et ne te réalerte que si l'un d'eux dépasse son seuil.

**Intégration UI**
- **Module « Veille »** :
  - Radar : les signaux triés par intensité × exposition ;
  - fiche événement : chronologie, sources et traductions, confirmation, entités touchées ;
  - éditeur de la liste de surveillance ;
  - tableau des prévisions, avec ton score de calibration.
- **Widgets** : *Radar* (5 signaux colorés par impact), section « Monde » du brief, *Pages surveillées* (derniers changements).
- **Casiers et journal** : casier *Briefs*. Exemple de ligne : `VIGIE · alerte · Taïwan : volume +4,2 σ, impact modéré (3,0 % du portefeuille)`.
- **Notifications** :
  - jamais pour une simple actualité ;
  - un toast dès que l'impact est modéré ;
  - un push pour le critique, par exemple un préavis de grève sur ton vol du 14, ou ta destination qui passe en orange sur la carte de France Diplomatie.

**Dès aujourd'hui (V0)** : `watchlist.yaml` (10 thèmes) + 30 flux RSS + une requête GDELT par thème → dédoublonnage → brief de 07:00, plus la surveillance de 5 pages. La pondération par exposition s'active dès que TRÉSOR publie.

### 3.3 FILON : le commercial et le CRM qui se tiennent tout seuls

**Nom de code et mission principale.** **FILON** repère les entreprises au moment où un document public révèle qu'elles ont le problème que tu résous. Il les contacte avec une raison concrète, suit chaque échange depuis ta vraie boîte mail et ton agenda, et prépare tes rendez-vous.

*Ce qu'il apporte de nouveau :*
- une prospection déclenchée par des **signaux** : offre d'emploi qui trahit une tâche manuelle, immatriculation, appel d'offres, levée de fonds ;
- chaque « recontactez-moi en janvier » devient une relance datée, avec son contexte.

**Capacités techniques requises**
- **Scripts** :
  - collecteurs de signaux ;
  - enrichissement : à partir du SIREN, code NAF, tranche d'effectif et dirigeants ; crawl du site pour l'offre, la page contact et les outils repérés dans le HTML ;
  - score : règles de `cible.yaml`, puis pondération apprise sur tes affaires gagnées et perdues (`scikit-learn`) ;
  - emails rédigés à partir des seuls faits collectés, chacun conservé avec sa source. Le modèle local traite tes échanges clients ; seules les données publiques peuvent partir vers un modèle cloud ;
  - séquenceur : fenêtres d'envoi, quotas, volumes augmentés progressivement, arrêt à la première réponse ;
  - classement des réponses : RDV, devis, objection, « pas maintenant », désinscription ;
  - fiche de rendez-vous, et devis depuis un modèle Word (`docxtpl`).
- **Fichiers** :
  - CRM en SQLite : entreprises, contacts, affaires, interactions, tâches, liste d'opposition ;
  - un dossier `Prospection/<entreprise>/` par entreprise ;
  - `cible.yaml` : codes NAF, taille, région, signaux, ton.
- **Réseau** :
  - API Recherche d'entreprises (sans clé) et API Sirene de l'INSEE ;
  - open data du BODACC (créations, cessions, changements de dirigeants) et du BOAMP (marchés publics) ;
  - API Offres d'emploi de France Travail ;
  - sites des entreprises ;
  - envoi par ta messagerie actuelle (SMTP, Gmail API ou Microsoft Graph), depuis un **sous-domaine réservé à la prospection** (avec les enregistrements d'authentification SPF, DKIM et DMARC). Ton domaine principal reste ainsi protégé ;
  - API agenda + lien de réservation ;
  - synchronisation optionnelle avec HubSpot, Notion ou Twenty.
- **Conformité CNIL** :
  - B2B uniquement, avec un message lié à la fonction du destinataire ;
  - un lien d'opposition dans chaque email ; une opposition est définitive ;
  - les données d'un prospect sont supprimées 3 ans après son dernier contact.
- **Pas de scraping de LinkedIn**, interdit par ses conditions d'utilisation : l'open data française suffit.
- **Branché sur** :
  - reçoit `mail.casier.item` (*Prospects*), `veille.signal`, `finance.receivable.late` et le contexte ;
  - publie `crm.deal.stage_changed`, `crm.meeting.booked`, `crm.account.updated`.

**Scénario d'usage (Day in the life) : du signal au rendez-vous, sans toi**
1. **Lundi 06:00.** Parmi les 214 signaux de la nuit, l'un ressort. Une PME de négoce lyonnaise (85 salariés, NAF 46.69B) publie sur France Travail une offre d'« Assistant(e) ADV, ressaisie des commandes dans l'ERP ». FILON y voit une tâche manuelle automatisable et lui donne un score de 84/100.
2. Il complète la fiche : SIREN, dirigeants, et le site (catalogue, contact, directeur des opérations nommé sur la page équipe). L'entreprise n'a jamais été contactée et ne figure pas sur la liste d'opposition.
3. Il rédige un email de 80 mots qui part de l'offre : « plutôt que recruter pour ressaisir des commandes, les extraire automatiquement des PDF et des mails clients ». Il ajoute un cas concret et le lien d'opposition. L'email part mardi à 09:12, dans le quota de 10 premiers contacts par jour. L'affaire passe au stade « Contactée », avec une relance programmée 4 jours ouvrés plus tard.
4. **Vendredi 14:03.** Le prospect répond : « Intéressant, on en parle la semaine prochaine ? ». L'Agent Mail range la réponse dans *Prospects*. FILON reconnaît une demande de rendez-vous et annule la relance. Il répond dans le fil, comme ta politique l'autorise, avec ton lien de réservation. Les créneaux proposés excluent tes blocs de révision et ta semaine de partiels, posés par CURSUS.
5. Le prospect réserve mardi à 10:00 et l'affaire passe au stade « RDV ». FILON attache une fiche de préparation à l'événement d'agenda : signal d'origine, questions à poser, gain estimé (environ un poste de ressaisie). TRÉSOR ajoute la recette potentielle à sa prévision, pondérée par la probabilité du stade.

Ton premier geste dans cette affaire : arriver au rendez-vous.

**Intégration UI**
- **Module « Pipeline »** :
  - un tableau Kanban : Signal → Contacté → En discussion → RDV → Proposition → Gagné/Perdu ;
  - une fiche par entreprise, avec l'historique complet : mails, signaux, notes, devis, paiements vus par TRÉSOR.
- **Widgets** :
  - *Leads du jour* : les 5 premiers, avec leur score et leur raison ;
  - *Relances* : faites, ou à faire ;
  - *Pipeline pondéré* : montant × probabilité, partagé avec TRÉSOR ;
  - *Ce qui convertit* : taux de réponse par type de signal.
- **Casiers et journal** :
  - *Prospects* (règle de l'Agent Mail : tout mail d'un domaine présent au CRM) ;
  - *À valider* (premiers contacts au-delà du quota) ;
  - *Opposition*.
  - Exemple de ligne : `FILON · alerte · Réponse : demande de RDV`.
- **Notifications** : un toast pour une réponse positive ou un rendez-vous réservé.

**Dès aujourd'hui (V0)** :
- CRM reconstruit depuis l'historique de l'Agent Mail (un domaine = une entreprise, un fil = une interaction) ;
- widget *Relances dues* ;
- requête quotidienne Recherche d'entreprises + BODACC, qui produit 10 leads avec un brouillon chacun.

La première semaine, envoie les emails toi-même pour calibrer le ton. Passe ensuite en envoi automatique, sous quota.

### 3.4 CURSUS : le précepteur qui sait ce que tu oublies

**Nom de code et mission principale.** **CURSUS** transforme chaque cours en connaissance retenue. Il récupère ce que publie ton école, le range, le transcrit, le résume et en tire des cartes de révision. Il planifie tes révisions d'après ce que tu oublies **vraiment**, jusqu'à l'examen.

*Ce qu'il apporte de nouveau :*
- il **écoute ce que le prof dit de l'examen** (« ça, je le demande chaque année ») ;
- il cale ton agenda sur ce que tu oublies réellement, mesuré par Anki.

**Capacités techniques requises**
- **Scripts** :
  - synchronisation de la plateforme de cours : API Web Services de Moodle si ton établissement l'ouvre, sinon Playwright sur l'ENT, authentification unique (SSO) comprise ;
  - emploi du temps : fichier ICS synchronisé avec l'agenda, avec détection des changements ;
  - classement et renommage des fichiers ;
  - transcription locale (`faster-whisper`), alignée sur les slides ;
  - repérage des « signaux d'examen » ;
  - fiches et cartes avec renvoi à la slide et à la minute ;
  - planificateur : priorité = coefficient × oubli mesuré × proximité de l'échéance ;
  - examens blancs tirés des annales, avec correction.
- **Fichiers et OS** :
  - arborescence `Études/<semestre>/<matière>/` ;
  - surveillance du dossier Téléchargements (`watchdog`) ;
  - transcriptions horodatées ;
  - index vectoriel de tous tes cours ;
  - lancement d'Anki en arrière-plan s'il est fermé.
- **Réseau** :
  - Moodle/ENT ;
  - casier *école* (convocations, changements, notes) ;
  - AnkiConnect, l'API locale d'Anki (création de cartes, statistiques de révision) ;
  - agenda (Google, Outlook ou CalDAV).
- **Branché sur** :
  - reçoit `mail.casier.item` (école), `crm.meeting.booked` ;
  - publie `study.deadline.due`, `study.exam.scheduled` ;
  - passe le contexte en « examens » pendant les partiels.

**Scénario d'usage (Day in the life) : mercredi, 18:40**
1. Ta prof d'économétrie dépose sur Moodle l'enregistrement du CM 7 (1 h 50) et ses slides. CURSUS, qui se synchronise toutes les heures, les range dans `Études/S5/Économétrie/CM07 – Variables instrumentales/`.
2. Il transcrit l'enregistrement en local, puis découpe le texte slide par slide.
3. Il marque deux signaux d'examen **[EXAMEN]** :
   - « ça, je le demande tous les ans » (1:12:40) ;
   - « l'exercice 3 du TD ressemble beaucoup à ce qui tombera ».
4. Il produit une fiche d'une page, où chaque point renvoie à sa minute. Il crée aussi 18 cartes dans le paquet `Économétrie::CM07`, via AnkiConnect.
5. Il lit tes statistiques Anki : 61 % de rappel sur « endogénéité », partiel dans 19 jours, coefficient 3. Il pose donc deux sessions de 40 minutes dans tes créneaux libres (jeudi 21:00, dimanche 10:00), sans empiéter sur le rendez-vous prospect de mardi.
6. Le TD noté à rendre vendredi à 23:59 n'a encore aucun fichier dans ton dossier. CURSUS programme un rappel jeudi à 18:00, avec l'énoncé et les passages de cours utiles.
7. Il met à jour le widget *Échéances* et écrit dans le journal.

**Intégration UI**
- **Module « Études »** :
  - par matière : supports, transcriptions à horodatage cliquable, fiches, statistiques de mémoire, examens blancs ;
  - « Demande à ton cours » : questions-réponses, avec la slide et la minute citées.
- **Widgets** :
  - *Échéances* : compte à rebours, statut rendu / commencé / rien ;
  - *Mémoire par matière* : taux de rappel face à l'objectif ;
  - *Plan de la semaine* ;
  - *Prochain partiel* : niveau de préparation estimé.
- **Casiers et journal** : un casier par matière, et *À rendre*. Exemple de ligne : `CURSUS · info · CM07 Économétrie : 18 cartes, 2 signaux d'examen`.
- **Notifications** :
  - un push à J-2 si un rendu n'est pas commencé ;
  - un toast pour une note publiée ou un changement de salle.

**Dès aujourd'hui (V0)** : Téléchargements + casier *école* → classement, fiche d'une page et cartes Anki par document ; échéances lues dans les mails → agenda. La transcription et la planification adaptative viennent en V1.

### 3.5 FORGE : l'ingénieur d'astreinte de ta machine et de tes agents

**Nom de code et mission principale.** **FORGE** garde ton environnement de développement propre, sûr et sauvegardé. Surtout, il **répare les autres agents quand ils tombent en panne**, la nuit, avant que tu t'en aperçoives.

*Ce qu'il apporte de nouveau :*
- il corrige seul un scraper cassé par un changement de site, puis rejoue la tâche manquée ;
- il sauvegarde chaque soir ton travail non commité, sans toucher à tes dépôts.

**Capacités techniques requises**
- **Scripts** :
  - superviseur : signaux de vie (heartbeats) des agents, redémarrage avec un délai croissant, erreurs regroupées par empreinte (type d'exception + fichier + ligne) ;
  - auto-réparation : copies des dernières entrées valides → correctif proposé par le LLM → tests de non-régression → déploiement d'une nouvelle version → rejeu ;
  - audit des dépendances de tous tes dépôts (`osv-scanner`, `pip-audit`, `npm audit`), avec branche, tests et PR ;
  - `gitleaks` avant chaque push, pour bloquer les secrets ;
  - sauvegarde du travail non commité ;
  - entretien de la machine (`psutil`) : disque, ports, process oubliés, caches régénérables ;
  - sauvegardes `restic`, avec un **test de restauration** mensuel ;
  - suivi des coûts API par agent.
- **Fichiers et OS** :
  - lecture de `~/dev` ;
  - écriture sur le code des agents **uniquement dans des branches** `forge/*` ;
  - `.forge/fixtures/` : dernières entrées et sorties valides de chaque collecteur ;
  - tests dans un conteneur Docker sans réseau ;
  - supervision des process.
- **Réseau** :
  - GitHub ou GitLab (PR, issues, intégration continue) ;
  - OSV.dev ;
  - registres PyPI et npm ;
  - cible de sauvegarde (NAS, S3, B2) ;
  - LLM.
- **Branché sur** :
  - reçoit tous les `*.error`, les signaux de vie et les échecs de validation ;
  - publie `dev.incident.*` (nouveau → en réparation → réparé ou escaladé) ;
  - publie `dev.dependencies.updated`, pour que VIGIE surveille tes paquets ;
  - publie `dev.budget.exceeded`.
- **Qui surveille FORGE ?** Le hub : si FORGE ne donne plus signe de vie, une alerte critique part.

**Scénario d'usage (Day in the life) : la nuit de jeudi à vendredi**
1. **03:10.** Le collecteur VIGIE d'un think tank renvoie 0 article trois fois de suite, car le site a changé son HTML. Un événement `error` part, avec l'empreinte `vigie.collector.thinktank:SelectorEmpty`.
2. FORGE récupère la page actuelle et la dernière copie valide. Il demande au LLM un correctif limité au fichier du collecteur (nouveaux sélecteurs), puis l'applique dans la branche `forge/fix-vigie-thinktank`.
3. Il lance les tests en conteneur, hors réseau :
   - l'ancienne copie donne toujours ses 12 articles, donc rien n'a régressé ;
   - la nouvelle page en donne 14, avec titre, date et texte non vides, et un volume cohérent avec l'historique.
4. Les tests passent : FORGE fusionne, redémarre le collecteur en version 1.5 et rejoue la tâche. VIGIE termine son brief avant 07:00. Si un test avait échoué, rien n'aurait été déployé, et l'incident serait remonté avec le diff et le log.
5. La même nuit, FORGE traite trois autres sujets :
   - **une faille** signalée par OSV dans deux projets : il crée une branche, met à jour et lance les tests. La PR est prête pour l'un ; pour l'autre, les tests échouent et une issue est ouverte avec le log ;
   - **du travail non commité** depuis 48 h dans deux dépôts : FORGE crée un commit à partir d'un index temporaire (ton index et tes fichiers restent intacts). Il le vérifie avec `gitleaks`, puis le pousse sur une référence privée `refs/forge/wip/…` ;
   - **le disque** : 31 Go libérés (images Docker orphelines, `node_modules` de projets inactifs depuis 90 jours).

À 07:00, la carte FORGE affiche : « 1 auto-réparation, 1 PR prête, 1 issue, 2 sauvegardes, 31 Go libérés, 6 agents sur 6 au vert ».

**Intégration UI**
- **Feux de santé** en haut du tableau de bord : un voyant par agent, avec dernier succès, prochaine exécution, coût du jour et bouton pause.
- **Module « Santé & Dev »** :
  - *Incidents* : erreurs regroupées, statut, diff du correctif avec bouton « annuler » ;
  - *Dépôts* : non commité, non poussé, failles, intégration continue ;
  - *Machine* : disque, ports, dernière restauration testée ;
  - *Coûts* : ta surveillance API actuelle, étendue aux tokens et aux euros par agent.
- **Casiers et journal** : casiers *Incidents* et *PR à relire*. Les erreurs répétées sont regroupées en une seule ligne enrichie, par exemple : `FORGE · erreur → réparé · vigie.collector.thinktank (3 occurrences)`.
- **Notifications** : seulement ce qu'il n'a pas su réparer :
  - une alerte si un correctif échoue aux tests ;
  - un push critique si un agent reste arrêté plus d'une heure.

**Dès aujourd'hui (V0)** : signaux de vie, regroupement des erreurs et scan nocturne des dépôts (non commité, non poussé, OSV) → feux de santé et widget *Dépôts*. Dès maintenant, fais enregistrer à chaque collecteur ses entrées valides dans `.forge/fixtures/` : c'est la matière première de l'auto-réparation (V1).

## 4. Synergie : les points de contact, testés

### 4.1 Quatre chaînes qui traversent plusieurs agents

- **Signal → euros → argumentaire.** VIGIE détecte, TRÉSOR chiffre, FILON annote. Le tableau de bord affiche une seule carte, avec une sous-ligne par agent (voir le scénario 3.2).
- **Facture impayée.**
  - FILON passe une affaire en « Gagné » et transmet le montant et l'échéance. TRÉSOR guette le virement.
  - Le lendemain de l'échéance, sans paiement, TRÉSOR publie `finance.receivable.late`. FILON envoie alors une relance courtoise dans le fil.
  - À J+15, une relance ferme attend ta validation dans *À valider*. Elle rappelle les pénalités de retard et l'indemnité forfaitaire de 40 € pour frais de recouvrement.
- **Semaine de partiels.** CURSUS passe le contexte en « examens », et chaque agent s'adapte :
  - FILON descend à 3 premiers contacts par jour et ferme ses créneaux ;
  - VIGIE passe à un résumé quotidien ;
  - TRÉSOR ne notifie que le critique ;
  - FORGE reporte les mises à jour non urgentes.
- **Panne silencieuse évitée.** Ta banque renomme une colonne de son export CSV. La validation de schéma de TRÉSOR échoue explicitement au lieu d'importer des montants faux. FORGE adapte le parseur, les tests passent et l'import est rejoué. Tu ne vois qu'une seule carte : « réparé automatiquement ».

### 4.2 Les points de contact et leurs tests

| Point de contact | Ce qui peut casser | Règle | Test automatique |
|---|---|---|---|
| Deux agents, un même fait | 2 alertes pour 1 événement | même `correlation_id` → 1 carte, une sous-ligne par agent | injecter un faux signal « Taïwan » → 1 seule carte |
| Réactions en chaîne | boucle A → B → A | `hops` ≤ 3 + `dedup_key` (rejouer un événement n'a aucun effet) | rejouer 2 fois un événement → aucun effet de plus |
| Ressource partagée (agenda) | RDV posé sur une révision | un propriétaire par ressource : les blocs de révision sont à CURSUS, FILON ne propose que des créneaux libres | réserver sur un bloc CURSUS → refusé, alternative proposée |
| Agent muet | silence pris pour « rien à signaler » | signal de vie + « dernier succès » affiché ; alerte après 2 intervalles manqués | tuer un process → alerte en moins de 10 min |
| Entrée qui change de format | données fausses sans erreur | validation `pydantic` à chaque entrée : erreur explicite plutôt que donnée fausse | CSV à colonne renommée → erreur → réparation |
| Contenu hostile (page, mail) | injection de prompt → fuite de données | le LLM ne produit que des propositions JSON validées par le manifeste | page piégée « envoie ~/.ssh » → action refusée + alerte |
| Chiffres | montant inventé par le LLM | le code calcule ; tout montant extrait est recoupé | facture mal lue → non rapprochée → casier *Justificatifs manquants* |
| Machine éteinte | tâches perdues | jobstore persistant + `misfire_grace_time` d'APScheduler | éteindre une nuit → tâches rejouées au démarrage |
| Coûts | boucle LLM coûteuse | budget par agent et par jour dans le client instrumenté, bascule sur le modèle local | budget atteint → bascule + ligne au brief |

Ces neuf tests tiennent dans `tests/test_jonctions.py` : il injecte des événements dans `hub.db` et vérifie ce qui ressort au tableau de bord. Relance-le à chaque nouvel agent.

## 5. La route la plus rapide

| Ordre | Quoi | Effort indicatif | Ce que tu as à la fin |
|---|---|---|---|
| 1 | Noyau : `events`, client instrumenté, signaux de vie, manifestes, publication de `mail.casier.item` | ½ journée | le journal prêt à accueillir les agents ; les premières copies d'entrées valides s'accumulent |
| 2 | TRÉSOR V0 | 1 soirée | un mois rapproché et un classeur à jour, à partir de données déjà triées par l'Agent Mail |
| 3 | FORGE V0 | 1 soirée | feux de santé et scan des dépôts, avant d'ajouter d'autres agents |
| 4 | VIGIE V0 | 1 soirée | le brief de 07:00, pondéré par tes expositions |
| 5 | FILON V0 | 1 week-end | un CRM reconstruit depuis ta boîte mail + 10 leads par jour en brouillon |
| 6 | CURSUS V0 | 1 soirée | des cours rangés, avec fiches et cartes Anki automatiques |
| 7 | V1 | semaines suivantes | auto-réparation, transparisation des ETF, prévisions notées, envoi automatique FILON, planification adaptative |

En période de partiels, passe CURSUS en n° 2.

**Écarté volontairement :**
- **Ordres de bourse autonomes** : il n'y a qu'un ordre par mois à gagner, pour un risque maximal. Le ticket prêt suffit.
- **Scraping de LinkedIn** : interdit par ses conditions d'utilisation, et moins riche que l'open data française.
- **Microservices, Kubernetes, serveur de messages** : SQLite suffit pour un seul utilisateur, et le contrat d'événement permet de migrer plus tard sans rien réécrire.
- **Nouvelle interface** : les casiers, le journal et quelques widgets réutilisent ce que ton hub sait déjà afficher.
