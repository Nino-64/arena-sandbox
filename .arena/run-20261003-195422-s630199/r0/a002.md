# Ton hub devient un OS personnel : 5 agents et le noyau qui les relie

Ton hub a déjà les deux pièces les plus précieuses d'un OS personnel : des **casiers**, où l'information arrive triée, et un **journal d'événements en temps réel**. J'en fais le système nerveux de l'ensemble. Les cinq agents ci-dessous sont des blocs indépendants : ils lisent les casiers, écrivent dans le journal et se parlent à travers lui. Pour chacun, tu trouveras la vision complète, puis ce que tu peux en coder dès aujourd'hui.

## 2. Le noyau (à coder en premier, environ une demi-journée)

Le noyau n'est pas un agent : c'est le code commun, l'équivalent du noyau d'un OS. Chaque agent est un process Python qui dispose de trois choses :
- un **manifeste**, qui fixe ses droits ;
- des **tâches planifiées**, via APScheduler avec un jobstore SQLite pour rattraper au démarrage ce qui a été manqué ;
- des **abonnements** à des sujets du journal.

**2.1 Un seul contrat d'événement.** Le journal sert à la fois d'écran de contrôle, de bus entre agents et de registre d'audit. En plus de l'agent, du titre et du contenu, chaque événement porte :
- un `topic` de la forme `domaine.objet.verbe` (ex. `finance.exposure.updated`) ;
- un niveau `severity` (voir 2.7) ;
- des `entities`, les clés communes (voir 2.3) ;
- une `dedup_key`, pour qu'un événement ne soit traité qu'une fois ;
- un `correlation_id` : un fait réel égale un fil ;
- un compteur `hops` contre les boucles.

Voici une version minimale, testée, utilisable aujourd'hui :

```python
# noyau/bus.py — journal + bus partagé : un fichier SQLite, zéro serveur
import json, sqlite3, time, uuid
from contextlib import closing

DB_PATH = "hub.db"

def _connect():
    # une connexion par appel : sûr depuis plusieurs threads et plusieurs process
    return closing(sqlite3.connect(DB_PATH, isolation_level=None, timeout=10))

with _connect() as db:
    db.execute("PRAGMA journal_mode=WAL")  # lectures possibles pendant les écritures
    db.execute("""CREATE TABLE IF NOT EXISTS events(
      seq INTEGER PRIMARY KEY AUTOINCREMENT, id TEXT, ts REAL, agent TEXT,
      topic TEXT, severity TEXT, title TEXT, entities TEXT, payload TEXT,
      dedup_key TEXT UNIQUE, correlation_id TEXT, hops INTEGER)""")

def emit(agent, topic, title, severity="info", entities=(), payload=None,
         dedup_key=None, correlation_id=None, hops=0):
    """Publie un événement. Renvoie son id, ou None (doublon ou boucle)."""
    if hops > 3:                                   # coupe-circuit anti-boucle
        return None
    eid = uuid.uuid4().hex
    with _connect() as db:
        cur = db.execute(
            "INSERT OR IGNORE INTO events(id, ts, agent, topic, severity, title,"
            " entities, payload, dedup_key, correlation_id, hops)"
            " VALUES (?,?,?,?,?,?,?,?,?,?,?)",
            (eid, time.time(), agent, topic, severity, title,
             json.dumps(list(entities)),
             json.dumps(payload or {}, ensure_ascii=False),
             dedup_key, correlation_id or eid, hops))
        return eid if cur.rowcount else None

def read(topic_prefix, after_seq=0):
    """Abonnement par polling : chaque agent mémorise le dernier seq traité."""
    with _connect() as db:
        return db.execute(
            "SELECT * FROM events WHERE topic LIKE ? AND seq > ? ORDER BY seq",
            (topic_prefix + "%", after_seq)).fetchall()
```

Quand un agent réagit à un événement, il émet un nouvel événement avec le même `correlation_id` et `hops + 1`. Le jour où un simple fichier ne suffit plus, tu passes à NATS ou Redis Streams en gardant le même contrat.

**2.2 Le branchement sur l'existant.** Côté Agent Mail, il n'y a qu'une modification :
- à chaque message rangé, il publie `mail.casier.item` (casier, expéditeur, objet, chemins des pièces jointes) ;
- il accepte les demandes `mail.casier.create` et `mail.rule.create`, pour que les autres agents créent les casiers qui leur manquent (*impôts*, *école*, *Prospects*).

Ses casiers deviennent ainsi les files d'entrée de tout l'OS. Le casier devient aussi un objet universel : un agent peut y déposer un justificatif, un lead ou une PR à relire, sans nouvel écran à coder.

**2.3 Des clés de jointure communes.** Tous les agents désignent les choses avec les mêmes identifiants : `country:TW` (code ISO), `isin:…`, `siren:…`, `domain:…`, `pkg:pypi/requests`, `course:S5-ECONOMETRIE`. Une table `entities` relie les alias : « TSMC », « Taiwan Semiconductor », son ISIN et son ticker pointent vers la même ligne. VIGIE peut ainsi demander en une seule requête « qui, chez toi, est exposé à Taïwan ? ».

Une règle s'y ajoute : **chaque donnée a un seul propriétaire**. TRÉSOR possède les opérations et les positions, FILON les entreprises et les contacts, CURSUS les blocs de révision, FORGE le code des agents. Les autres agents n'écrivent jamais directement dans ces données : ils envoient une demande au propriétaire.

**2.4 Un contexte partagé.** Une ligne `context` contient le `mode` (normal, examens, voyage, vacances) et les heures calmes. CURSUS la règle pour tes partiels, l'Agent Mail pour tes voyages, et toi par un interrupteur. Chaque agent la lit avant d'agir.

**2.5 Un seul client HTTP/LLM instrumenté.** Tous les agents passent par la même surcouche (wrapper). Elle écrit chaque requête dans le journal : hôte, statut, latence, tokens, coût. Ta surveillance actuelle des requêtes API couvre donc aussi les cinq agents. La surcouche applique en plus le budget de chaque agent et envoie les données sensibles au modèle local.

**2.6 Autonomie graduée et garde-fous.** C'est ce qui permet de tout laisser tourner sans surveillance. Voici le manifeste de FILON en exemple :

```yaml
# agents/filon/manifest.yaml
fichiers: {lecture: ["~/Prospection", "~/hub/hub.db"], ecriture: ["~/Prospection"]}
web_public: lecture_seule        # crawl de sites : GET sans cookies ni identifiants
api: ["recherche-entreprises.api.gouv.fr", "api.insee.fr", "*.opendatasoft.com",
      "api.francetravail.io", "www.googleapis.com"]   # seuls hôtes qui reçoivent des identifiants
commandes: []                    # aucune commande système
budget_llm_eur_jour: 0.80
autonomie:
  reponse_dans_un_fil_engage: auto
  premier_contact: {auto_sous_plafond: 10/jour}   # au-delà → casier « À valider »
  suppression_de_donnees: validation
```

- **Le LLM propose, le code décide.** Tout ce qui vient du web ou d'un mail est considéré comme non fiable. Le LLM ne renvoie que des propositions en JSON. Le code les valide avec `pydantic`, puis les compare au manifeste. Une page piégée qui « demande » d'envoyer tes fichiers ne déclenche donc rien.
- **Secrets** : ils restent dans le trousseau de l'OS (`keyring`) et sont masqués dans les logs et les prompts.
- **Suppressions** : aucune donnée à toi n'est supprimée directement, tout passe 30 jours en quarantaine. Seuls les caches régénérables sont nettoyés sans délai : images Docker orphelines, `node_modules` accompagnés d'un fichier de verrouillage (lockfile).
- **Contrôle** : les correctifs de code et leurs tests tournent dans un conteneur sans réseau. Chaque agent a un bouton pause, il existe un arrêt général, et chaque action est tracée dans le journal.

**2.7 La remontée dans ton tableau de bord.**

| Niveau | Exemples | Où ça apparaît |
|---|---|---|
| `info` | tâche terminée, 148 opérations importées | journal |
| `brief` | 10 leads du jour, note de veille | journal + badge du widget + brief du matin |
| `alerte` | abonnement en double, signal d'impact modéré, réponse positive d'un prospect | toast dans le hub + panneau *Alertes* |
| `critique` | débit suspect, rendu non commencé à J-2, agent arrêté depuis plus d'une heure | notification système + push sur le téléphone |
| `erreur` | exception d'un agent | journal, regroupée par FORGE ; passe en `alerte` si l'auto-réparation échoue |

## 3. Les cinq agents

### 3.1 TRÉSOR : le directeur financier qui clôture ton mois pendant que tu dors

**Nom de code et mission principale.** **TRÉSOR** tient, sans aucune saisie, une image exacte de ton argent, présent et à venir. Chaque opération est catégorisée et rattachée à son justificatif. Chaque ETF est décomposé jusqu'à ses lignes. Chaque mois est clôturé, et ton tableau de bord financier se met à jour tout seul.

*Ce qui sort de l'ordinaire :*
- il rapproche chaque opération de sa facture, à partir des casiers que l'Agent Mail remplit déjà ;
- il décompose tes ETF ligne par ligne (transparisation) pour révéler ton exposition réelle par entreprise, pays et devise ;
- sa prévision de trésorerie à 90 jours voit les découverts avant ta banque.

**Capacités techniques requises**
- **Scripts Python** :
  - import des relevés : CSV/OFX avec `ofxtools`, PDF avec `pdfplumber`, factures électroniques Factur-X avec la bibliothèque `factur-x` ;
  - catégorisation : règles YAML d'abord, modèle local pour le reste ;
  - rapprochement : montant exact, date à ±5 jours, nom du marchand comparé de façon approximative avec `rapidfuzz` ;
  - détection des abonnements, hausses de prix, doublons, frais et débits inhabituels ;
  - calculs avec `pandas`/DuckDB : patrimoine net, taux d'épargne, rendement réel de tes versements (XIRR), écart à ton allocation cible, transparisation ;
  - projection de trésorerie à partir des récurrences, des échéances lues dans les casiers et des recettes attendues de FILON ;
  - écriture de ton classeur Budget, avec `openpyxl` (Excel) ou `gspread` (Google Sheets).
- **Fichiers** :
  - casiers *banque*, *factures* et *impôts* ;
  - grand livre `finances.duckdb` ;
  - justificatifs renommés, par exemple `Finances/Justificatifs/2026/09/2026-09-12_Operateur_29,99.pdf` ;
  - `positions.yaml` (ISIN, quantités, enveloppe, cible), tant qu'aucune API courtier n'est branchée.
- **Réseau** :
  - banque : un agrégateur DSP2 en lecture seule, par exemple Enable Banking (vérifie ses conditions actuelles d'usage personnel). La DSP2 impose de te réauthentifier tous les 180 jours ; TRÉSOR te le rappelle 7 jours avant ;
  - courtier : Flex Web Service si tu es chez Interactive Brokers, sinon les exports CSV et les avis d'opéré rangés par l'Agent Mail ;
  - cours de clôture via `yfinance` (suffixe `.PA` pour Euronext Paris), avec une source de secours ;
  - taux de change de la Banque centrale européenne ;
  - fichiers de composition publiés par les émetteurs d'ETF (iShares, Amundi, Xtrackers…) ;
  - Playwright, en session persistante, pour récupérer une facture manquante sur un espace client sans double authentification.
- **IA** : extraction et catégorisation, en local. **Aucun montant ne vient du LLM** : il lit et rédige, le code calcule. Chaque montant extrait est recoupé entre la facture et l'opération.
- **Branché sur** :
  - reçoit `mail.casier.item`, `crm.deal.*` et `veille.signal` ;
  - publie `finance.exposure.updated`, `finance.cashflow.alert`, `finance.anomaly`, `finance.receivable.late` et `finance.month.closed`.

**Scénario d'usage (Day in the life) : la clôture de septembre, le 2 octobre à 05:30**
1. TRÉSOR récupère les 148 opérations de septembre, par l'API DSP2 (en V0, depuis le relevé rangé dans *banque*). Les règles en catégorisent 139, le modèle local les 9 autres.
2. Sur 127 débits, 121 retrouvent leur facture dans *factures*. Pour 4 autres, TRÉSOR ouvre l'espace client des fournisseurs configurés et télécharge les PDF manquants. Les 2 derniers débits vont dans le casier *Justificatifs manquants*.
3. Il repère trois anomalies :
   - ton assurance habitation augmente de 17 % à l'échéance. Il prépare en brouillon la lettre de résiliation (possible à tout moment après un an, grâce à la loi Hamon) et deux demandes de devis ;
   - deux abonnements de streaming sont facturés en double depuis août ;
   - des frais de tenue de compte sont réapparus.
4. Il écrit l'onglet « 2026-09 » de ton classeur Budget (patrimoine net, taux d'épargne) et archive un PDF de synthèse.
5. Il recalcule ton exposition réelle à partir des compositions du jour : par exemple Taïwan 3,0 % dont TSMC 1,7 %, et dollar 60 %. Ta poche Émergents est à 16 % pour une cible de 20 %. Il affecte donc tout ton versement programmé du 5 (500 €) à l'ETF Émergents et prépare le ticket d'ordre. Rééquilibrer sans vendre évite les frais de cession et, hors PEA, l'impôt sur la plus-value.
6. Il projette ta trésorerie. L'assurance auto annuelle (le 18), puis le prélèvement d'impôt annoncé dans *impôts* (le 20), feront passer ton compte courant sous 150 €. Il t'alerte 18 jours avant, avec le virement à faire depuis ton livret.
7. Il publie `finance.exposure.updated`, et VIGIE place Taïwan plus haut dans sa liste de surveillance.

À ton réveil, le mois est clôturé, le classeur à jour et trois décisions sont préparées, sans aucune saisie. Un seul geste reste manuel, par choix : passer l'ordre. Il ne devient automatisable que chez un courtier doté d'une API, et sous un plafond.

**Intégration UI**
- **Module « Finances »** dans la barre latérale, sur le modèle de l'Agent Mail, avec quatre onglets : Mois · Portefeuille · Prévision · Justificatifs.
- **Widgets** :
  - *Patrimoine net* : chiffre + courbe sur 12 mois ;
  - *Trésorerie J+90* : solde projeté, zone rouge sous ton seuil, gros prélèvements en jalons ;
  - *Allocation vs cible* ;
  - *Exposition réelle* : principaux pays, entreprises et devises ;
  - *Rapprochement* : 125/127 débits justifiés.
- **Casiers** : *Justificatifs manquants* et *À résilier*.
- **Journal** :
  - `TRÉSOR · info · Clôture de septembre : 148 opérations, 2 justificatifs manquants`
  - `TRÉSOR · alerte · Abonnement facturé en double (2 × 13,49 €)`
- **Notifications** : un toast pour les décisions du mois. Un push immédiat pour un débit inhabituel : marchand inconnu au-delà de 300 €, ou montant trois fois supérieur à l'habitude.

**Dès aujourd'hui (V0)** :
- relevé du casier *banque* + factures du casier *factures* → catégorisation, rapprochement, onglet du mois ;
- `positions.yaml` + cours du soir → widget *Allocation vs cible*.

Tout part de données que l'Agent Mail trie déjà.

### 3.2 VIGIE : la veille qui ne te parle que de ce qui te touche

**Nom de code et mission principale.** **VIGIE** lit le monde à ta place, dans les sources internationales et officielles, en langue originale. Il ne te remonte que ce qui touche **tes** expositions :
- ce que tu possèdes (via TRÉSOR) ;
- ceux à qui tu vends (via FILON) ;
- ce que ton code utilise (via FORGE) ;
- là où tu vas (casier *voyages*).

Chaque signal arrive avec sa source primaire et un niveau de confiance.

*Ce qui sort de l'ordinaire :*
- l'importance d'une nouvelle est mesurée par rapport à toi (intensité × exposition) ;
- une escalade est repérée par anomalie statistique, plutôt que par mot-clé ;
- VIGIE **note ses propres prédictions**, pour apprendre quelles sources sont fiables.

**Capacités techniques requises**
- **Scripts** :
  - flux RSS (`feedparser`) d'une liste choisie : ministères, banques centrales, think tanks, presse spécialisée ;
  - API GDELT DOC 2.0 : presse mondiale mise à jour toutes les 15 minutes, avec volumes et tonalité par thème et par pays ;
  - extraction du texte avec `trafilatura`, et Playwright pour les sites en JavaScript ;
  - traduction, puis regroupement des articles en événements (embeddings + seuil de similarité) ;
  - extraction des entités, rattachées aux clés communes ;
  - détection d'escalade : écart à la moyenne mobile sur 30 jours, mesuré en écarts-types ;
  - comparaison des pages surveillées avec leur version précédente, pour en extraire les changements ;
  - registre de prévisions datées, notées ensuite avec le score de Brier.
- **Fichiers** :
  - archive locale de chaque article retenu (Markdown + index vectoriel `sqlite-vec`). C'est ta base de renseignement privée, interrogeable sur des années ;
  - `watchlist.yaml` : thèmes, pays et pages à surveiller ;
  - briefs archivés.
- **Réseau** :
  - RSS/HTTP et GDELT ;
  - liste consolidée des sanctions de l'UE et liste OFAC ;
  - Journal officiel, via l'API Légifrance (portail PISTE) ;
  - « Conseils aux voyageurs » de France Diplomatie, pour tes destinations ;
  - séries économiques de la BCE et de FRED ;
  - en option, collecte 24 h/24 sur un VPS.
- **IA** : regroupement, traduction, synthèse. Chaque affirmation d'une note renvoie à sa source ; sans source, elle est marquée « non confirmé ».
- **Branché sur** :
  - reçoit `finance.exposure.updated`, `crm.account.updated`, `dev.dependencies.updated` et `mail.casier.item` (voyages) ;
  - publie `veille.signal` (score d'impact + entités touchées), `veille.brief.ready` et `veille.page.changed`.

**Scénario d'usage (Day in the life) : mardi, 05:50**
1. Le volume d'articles GDELT qui associent Taïwan à « exercices militaires / blocus » monte à 4,2 écarts-types au-dessus de sa moyenne sur 30 jours.
2. VIGIE regroupe 37 articles en 9 langues en un seul événement et traduit les sources chinoises et taïwanaises. Il retrouve la source primaire, un communiqué du ministère taïwanais de la Défense, et passe l'événement en statut « confirmé ».
3. Il interroge les clés communes :
   - TRÉSOR indique 3,0 % de ton portefeuille exposé à Taïwan, dont TSMC 1,7 % ;
   - FILON a deux comptes qui importent de l'électronique d'Asie ;
   - aucun voyage n'est prévu dans la zone.
4. L'impact est jugé modéré. VIGIE demande alors un stress test à TRÉSOR : un recul de 20 % des actions taïwanaises coûterait 0,6 % de ton portefeuille.
5. Il rédige une note de six lignes : faits confirmés, inconnues, et trois indicateurs à suivre (NOTAM et avertissements de navigation dans la zone, primes d'assurance maritime, ouverture de la Bourse de Taipei). Il ajoute une ligne de contexte sur les deux fiches FILON. Il enregistre aussi une prévision datée, marquée comme estimation (« blocus effectif sous 30 jours : 7 % »), qu'il notera lui-même dans 30 jours.
6. À 07:00, l'événement ouvre le brief du matin et s'affiche en orange dans le Radar, avec son impact chiffré. Les jours suivants, VIGIE suit les trois indicateurs en silence. Il ne te réalerte que si l'un d'eux franchit son seuil.

**Intégration UI**
- **Module « Veille »** :
  - Radar : les signaux actifs, triés par intensité × exposition ;
  - fiche événement : chronologie, sources et traductions, statut de confirmation, entités touchées, liens vers TRÉSOR et FILON ;
  - éditeur de la liste de surveillance ;
  - tableau des prévisions, avec ton score de calibration.
- **Widgets** :
  - *Radar* : 5 signaux, colorés selon l'impact ;
  - section « Monde » du brief du matin ;
  - *Pages surveillées* : derniers changements, avec les passages modifiés.
- **Casier** : *Briefs*, quotidiens et hebdomadaires, avec recherche.
- **Journal** : `VIGIE · alerte · Taïwan : volume +4,2 σ, impact modéré (3,0 % du portefeuille)`
- **Notifications** :
  - jamais pour une simple actualité ;
  - un toast dès que l'impact est modéré ;
  - un push pour le critique, par exemple un préavis de grève qui touche ton vol du 14, ou la zone de ta destination qui passe en orange sur la carte de France Diplomatie.

**Dès aujourd'hui (V0)** : `watchlist.yaml` (10 thèmes) + 30 flux RSS + une requête GDELT par thème → dédoublonnage → brief de 07:00 dans le hub. Ajoute la surveillance des changements sur 5 pages. La pondération par exposition s'active dès que TRÉSOR publie.

### 3.3 FILON : le commercial et le CRM qui se tiennent tout seuls

**Nom de code et mission principale.** **FILON** prospecte et tient ton CRM à ta place :
- il repère les entreprises au moment précis où un document public révèle qu'elles ont le problème que tu résous ;
- il les contacte avec une raison concrète ;
- il suit chaque échange à partir de ta vraie boîte mail et de ton agenda ;
- il prépare tes rendez-vous.

*Ce qui sort de l'ordinaire :*
- une prospection sur **signaux** : une offre d'emploi qui trahit une tâche manuelle, une immatriculation, un appel d'offres, une levée de fonds ;
- chaque « recontactez-moi en janvier » reçu par mail devient une relance datée, avec son contexte.

**Capacités techniques requises**
- **Scripts** :
  - collecteurs de signaux ;
  - enrichissement : à partir du SIREN, code NAF, tranche d'effectif et dirigeants. Crawl du site pour l'offre, la page contact et les outils utilisés (repérés à leur trace dans le code HTML) ;

  - API agenda + lien de réservation ;
  - synchronisation optionnelle vers HubSpot, Notion ou Twenty.
- **Conformité intégrée** (règles de la CNIL) :
  - B2B uniquement, avec un message en rapport avec la fonction du destinataire ;
  - un lien d'opposition dans chaque email, et une liste d'opposition respectée pour toujours ;
  - les données d'un prospect sont purgées 3 ans après le dernier contact venu de lui.
- **Pas de scraping de LinkedIn** : ses conditions d'utilisation l'interdisent, et l'open data française donne de meilleurs signaux.
- **Branché sur** :
  - reçoit `mail.casier.item` (*Prospects*), `veille.signal`, `finance.receivable.late` et le contexte partagé ;
  - publie `crm.deal.stage_changed`, `crm.meeting.booked` et `crm.account.updated`.

### 3.4 CURSUS : le précepteur qui sait ce que tu oublies

**Nom de code et mission principale.** **CURSUS** transforme chaque cours en connaissance réellement retenue. Il récupère tout ce que publie ton école, le range, le transcrit, le résume et en tire des cartes de révision. Il planifie ensuite tes révisions d'après ce que tu oublies **vraiment**, jusqu'au jour de l'examen.

*Ce qui sort de l'ordinaire :*
- il **écoute ce que le prof dit de l'examen** (« ça, je le demande chaque année ») ;
- il organise ton agenda selon ce que tu oublies réellement, plutôt que selon un planning théorique.

**Capacités techniques requises**
- **Scripts** :
  - synchronisation de la plateforme de cours : API Web Services de Moodle quand ton établissement l'ouvre, sinon Playwright sur l'ENT, connexion unique (SSO) comprise ;
  - emploi du temps : fichier ICS synchronisé avec ton agenda, avec détection des changements de salle ou d'horaire ;
  - classement et renommage des fichiers ;
  - transcription locale avec `faster-whisper`, puis alignement de la transcription sur les slides par similarité de texte ;
  - repérage des « signaux d'examen » dans la transcription ;
  - fiches et cartes générées par le LLM, chacune avec un renvoi à sa slide et à sa minute ;
  - planificateur : priorité = coefficient × oubli mesuré × proximité de l'échéance ;
  - examens blancs construits à partir des annales, avec une correction commentée.
- **Fichiers et OS** :
  - arborescence `Études/<semestre>/<matière>/` ;
  - surveillance du dossier Téléchargements (`watchdog`), pour classer aussi ce que tu récupères à la main ;
  - transcriptions horodatées en Markdown ;
  - index vectoriel de tous tes cours ;
  - lancement d'Anki en arrière-plan s'il est fermé.
- **Réseau** :
  - Moodle/ENT ;
  - casier *école* de l'Agent Mail : convocations, changements, notes ;
  - AnkiConnect, l'API locale d'Anki, pour créer des cartes et lire tes statistiques de révision ;
  - API agenda : Google, Outlook ou CalDAV.
- **Branché sur** :
  - reçoit `mail.casier.item` (école) et `crm.meeting.booked` ;
  - publie `study.deadline.due` et `study.exam.scheduled` ;
  - règle le contexte sur « examens » pendant tes partiels.

**Scénario d'usage (Day in the life) : mercredi, 18:40**
1. Ta prof d'économétrie dépose sur Moodle l'enregistrement du CM 7 (1 h 50) et ses slides. CURSUS, qui se synchronise toutes les heures, les télécharge et les range dans `Études/S5/Économétrie/CM07 – Variables instrumentales/`.
2. Il lance la transcription en local, puis découpe le texte slide par slide.
3. Il repère deux signaux d'examen et les marque **[EXAMEN]** dans la fiche :
   - « ça, je le demande tous les ans » (à 1:12:40) ;
   - « l'exercice 3 du TD ressemble beaucoup à ce qui tombera ».
4. Il produit une fiche d'une page, où chaque point renvoie à sa minute d'enregistrement. Il crée aussi 18 cartes dans le paquet `Économétrie::CM07` et les envoie par AnkiConnect.
5. Il lit tes statistiques Anki : 61 % de rappel sur « endogénéité », partiel dans 19 jours, coefficient 3. Il pose donc deux sessions de 40 minutes dans tes créneaux libres (jeudi 21:00, dimanche 10:00), sans toucher au rendez-vous prospect de mardi.
6. Il constate que le TD noté à rendre vendredi à 23:59 n'a encore aucun fichier dans ton dossier de travail. Il programme un rappel pour jeudi 18:00, avec l'énoncé et les passages de cours utiles.
7. Il met à jour le widget *Échéances* et écrit une ligne au journal.

**Intégration UI**
- **Module « Études »** :
  - par matière : les supports, les transcriptions (un clic sur un horodatage ouvre l'enregistrement à ce moment), les fiches, les statistiques de mémoire, les examens blancs ;
  - « Demande à ton cours » : questions-réponses sur tes propres supports, avec la slide et la minute citées.
- **Widgets** :
  - *Échéances* : compte à rebours, avec le statut rendu / commencé / rien ;
  - *Mémoire par matière* : taux de rappel mesuré face à l'objectif ;
  - *Plan de la semaine* ;
  - *Prochain partiel* : jours restants et niveau de préparation estimé.
- **Casiers** : un par matière (créé automatiquement), et *À rendre*.
- **Journal** : `CURSUS · info · CM07 Économétrie : 18 cartes, 2 signaux d'examen`
- **Notifications** : un push à J-2 si un rendu n'est pas commencé ; un toast pour une note publiée ou un changement de salle.

**Dès aujourd'hui (V0)** :
- surveillance de Téléchargements + casier *école* → classement automatique, avec une fiche d'une page et des cartes Anki pour chaque document ;
- échéances lues dans les mails → agenda.

La transcription et la planification adaptative arrivent en V1.

### 3.5 FORGE : l'ingénieur d'astreinte de ta machine et de tes agents

**Nom de code et mission principale.** **FORGE** garde ton environnement de développement propre, sûr et sauvegardé. Surtout, il **répare les autres agents quand ils tombent en panne**, la nuit, avant que tu t'en aperçoives.

*Ce qui sort de l'ordinaire :* FORGE corrige lui-même un scraper devenu inopérant parce que le site a changé, puis rejoue la tâche manquée. Il sauvegarde aussi chaque soir ton travail non commité, sans toucher à tes dépôts.

**Capacités techniques requises**
- **Scripts** :
  - superviseur : heartbeats, redémarrage avec un délai croissant entre les tentatives, regroupement des erreurs par empreinte (type d'exception + fichier + ligne) ;
  - auto-réparation, en cinq étapes : instantanés des entrées valides → correctif proposé par le LLM → tests de non-régression → déploiement versionné → rejeu ;
  - audit des dépendances de tous tes dépôts avec `osv-scanner`, `pip-audit` et `npm audit`. Pour chaque faille : une branche de mise à jour, des tests et une PR ;
  - `gitleaks` avant chaque push ;
  - sauvegarde de ton travail non commité ;
  - entretien de la machine avec `psutil` : disque, ports, process oubliés, nettoyage des caches régénérables ;
  - sauvegardes `restic`, avec un **test de restauration** chaque mois ;
  - suivi des coûts API par agent.
- **Fichiers et OS** :
  - lecture de `~/dev` ;
  - écriture sur le code des agents **uniquement dans des branches** `forge/*` ;
  - dossier `.forge/fixtures/`, qui garde les dernières entrées et sorties valides de chaque collecteur ;
  - correctifs et tests exécutés dans un conteneur Docker sans réseau ;
  - supervision des process.
- **Réseau** :
  - GitHub ou GitLab : PR, issues, statut de l'intégration continue (CI) ;
  - OSV.dev, la base de failles connues ;
  - registres PyPI et npm ;
  - cible de sauvegarde : NAS, S3 ou B2 ;
  - LLM.
- **Branché sur** :
  - reçoit **tous** les `*.error`, les heartbeats et les échecs de validation de schéma ;
  - publie `dev.incident.*` (nouveau → en réparation → réparé ou escaladé) ;
  - publie `dev.dependencies.updated`, pour que VIGIE surveille les incidents qui touchent tes paquets ;
  - publie `dev.budget.exceeded`.
- **Qui surveille FORGE ?** Le hub lui-même : si FORGE ne donne plus signe de vie, une alerte critique part.

**Scénario d'usage (Day in the life) : la nuit de jeudi à vendredi**
1. **03:10.** Le collecteur de VIGIE pour un think tank renvoie 0 article trois fois de suite : le site a changé sa structure HTML. Un événement `error` part, avec l'empreinte `vigie.collector.thinktank:SelectorEmpty`.
2. FORGE récupère la page actuelle et le dernier instantané valide dans `.forge/fixtures/`. Il demande au LLM un correctif limité au fichier du collecteur (nouveaux sélecteurs), puis l'applique dans la branche `forge/fix-vigie-thinktank`.
3. Il lance les tests en conteneur, hors réseau, sur les deux instantanés :
   - l'ancien donne toujours ses 12 articles : pas de régression ;
   - le nouveau en donne 14, avec titre, date et texte non vides, et un volume cohérent avec l'historique.
4. Les tests passent. FORGE fusionne la branche, redémarre le collecteur en version 1.5 et rejoue la tâche manquée. VIGIE termine son brief avant 07:00. Si un test avait échoué, rien n'aurait été déployé et l'incident serait remonté avec le diff et le log.
5. La même nuit, FORGE traite trois autres sujets :
   - **une faille** : OSV signale une dépendance vulnérable dans deux de tes projets. FORGE crée une branche, met la dépendance à jour et lance les tests. Ils passent sur un projet (PR prête) et échouent sur l'autre (issue ouverte avec le log) ;
   - **du travail non commité** : deux dépôts en ont depuis plus de 48 h. FORGE construit un commit séparé sur un index temporaire, ce qui laisse ton index et tes fichiers intacts. Il le fait vérifier par `gitleaks`, puis le pousse sur une référence privée `refs/forge/wip/…` ;
   - **le disque** : 31 Go libérés (images Docker orphelines, `node_modules` de projets inactifs depuis 90 jours).

À 07:00, la carte FORGE affiche : « 1 auto-réparation (VIGIE), 1 PR prête, 1 issue, 2 sauvegardes de travail en cours, 31 Go libérés, 6 agents sur 6 au vert ».

**Intégration UI**
- **Feux de santé** en haut du tableau de bord : un voyant par agent (vert, orange ou rouge), avec le dernier succès, la prochaine exécution, le coût du jour et un bouton pause.
- **Module « Santé & Dev »** :
  - *Incidents* : erreurs regroupées, statut de réparation, diff du correctif avec un bouton « annuler » qui revient à la version précédente ;
  - *Dépôts* : non commité, non poussé, failles, CI ;
  - *Machine* : disque, process, ports, date de la dernière restauration testée ;
  - *Coûts* : prolonge ta surveillance API actuelle, avec les requêtes, les tokens et les euros par agent.
- **Casiers** : *Incidents*, *PR à relire*.
- **Journal** : FORGE enrichit chaque erreur, quel que soit l'agent (empreinte, nombre d'occurrences, statut), pour que le journal ne soit pas noyé sous les répétitions. Exemple : `FORGE · erreur → réparé · vigie.collector.thinktank (3 occurrences)`
- **Notifications** : seulement ce qu'il n'a pas su réparer. Une alerte si un correctif échoue aux tests ; un push critique si un agent reste arrêté plus d'une heure.

**Dès aujourd'hui (V0)** :
- heartbeats, regroupement des erreurs dans le journal et scan nocturne des dépôts (non commité, non poussé, OSV) → feux de santé et widget *Dépôts* ;
- dès maintenant, chaque collecteur enregistre ses entrées valides dans `.forge/fixtures/`. C'est la matière première de l'auto-réparation (V1).

## 4. Synergie : les points de contact, testés

### 4.1 Quatre chaînes qui traversent plusieurs agents

- **Signal → euros → argumentaire.** VIGIE détecte, TRÉSOR chiffre, FILON annote ses fiches. Le tableau de bord affiche une seule carte, avec une sous-ligne par agent (voir le scénario 3.2).
- **Facture impayée.**
  - FILON passe une affaire en « Gagné » et transmet le montant et l'échéance de ta facture. TRÉSOR guette le virement.
  - Si rien n'est arrivé le lendemain de l'échéance, TRÉSOR publie `finance.receivable.late`. FILON envoie alors une relance courtoise dans le fil existant.
  - À J+15, une relance ferme est prête : pénalités de retard + indemnité forfaitaire de 40 € pour frais de recouvrement. Elle attend ta validation dans *À valider*.
  - Au paiement, TRÉSOR clôt le dossier des deux côtés.
- **Semaine de partiels.** CURSUS règle le contexte sur « examens », et chaque agent s'adapte :
  - FILON descend à 3 premiers contacts par jour et ferme ses créneaux de rendez-vous ;
  - VIGIE passe à un digest quotidien ;
  - TRÉSOR ne notifie que le critique ;
  - FORGE reporte les mises à jour non urgentes.

  La semaine suivante, tout reprend.
- **Panne silencieuse évitée.** Ta banque renomme une colonne de son export CSV. La validation de schéma de TRÉSOR échoue explicitement, au lieu d'importer des montants faux. FORGE adapte le parseur sur l'échantillon, les tests passent et TRÉSOR rejoue l'import. Tu ne vois qu'une carte : « réparé automatiquement ».

### 4.2 Les points de contact et leurs tests

| Point de contact | Ce qui peut casser | Règle | Test automatique |
|---|---|---|---|
| Deux agents, un même fait | 2 alertes pour 1 événement | même `correlation_id` → 1 carte, une sous-ligne par agent | injecter un faux signal « Taïwan » → 1 seule carte |
| Réactions en chaîne | boucle A → B → A | `hops` ≤ 3 + `dedup_key` (un événement rejoué n'a aucun effet) | rejouer 2 fois un événement → aucun effet de plus |
| Ressource partagée (agenda) | RDV posé sur une révision | un propriétaire par ressource : les blocs de révision sont à CURSUS, FILON ne propose que des créneaux libres | réserver sur un bloc CURSUS → refusé, alternative proposée |
| Agent muet | silence pris pour « rien à signaler » | heartbeat + « dernier succès » affiché ; alerte après 2 intervalles manqués | tuer un process → alerte en moins de 10 min |
| Entrée qui change de format | données fausses sans erreur | validation `pydantic` à chaque entrée de données : erreur explicite plutôt que donnée fausse | CSV à colonne renommée → erreur → réparation |
| Contenu hostile (page, mail) | injection de prompt → fuite de données | le LLM ne produit que des propositions JSON validées par le manifeste | page piégée « envoie ~/.ssh » → action refusée + alerte |
| Chiffres | montant inventé par le LLM | le code calcule ; tout montant extrait est recoupé | facture mal lue → non rapprochée → casier *Justificatifs manquants* |
| Machine éteinte | tâches perdues | jobstore persistant + `misfire_grace_time` d'APScheduler | éteindre une nuit → tâches rejouées au démarrage |
| Coûts | boucle LLM coûteuse | budget par agent et par jour dans le client instrumenté, bascule sur le modèle local | budget atteint → bascule + ligne au brief |

Ces neuf tests tiennent dans un seul fichier, `tests/test_jonctions.py`. Il injecte des événements dans `hub.db` et vérifie ce qui ressort au tableau de bord. Lance-le à chaque fois que tu greffes un nouvel agent.

**Ce que j'ai volontairement écarté, parce que ça n'accélère rien :**
- **Le passage d'ordres de bourse autonome** : il n'y a qu'un ordre par mois à gagner, pour un risque maximal. Le ticket prêt suffit.
- **Le scraping de LinkedIn** : il est interdit par ses conditions d'utilisation, et moins riche que l'open data française.
- **Microservices, Kubernetes, serveur de messagerie dédié** : un fichier SQLite suffit pour un seul utilisateur. Le contrat d'événement te permettra de migrer plus tard sans rien réécrire.
- **Une nouvelle interface** : les casiers, le journal et quelques widgets réutilisent ce que ton hub sait déjà afficher.
